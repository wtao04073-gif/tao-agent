## M4-1 · 计量、配额与熔断

### 先做 spike，结论是「原计划不可行」

原本打算把配额熔断挂在 `before_request`（模型调用前）—— 这是最自然的位置：还没花钱就拦住。

[Spike 6](../spikes/06-metering-breaker/) 实测发现**这个钩子不能用于熔断**：

| 钩子 | 异常处理 | 有 `block` 通道 | 能否熔断 |
|---|---|---|---|
| `before_request` | catch 后只 `reportError`，**不重抛** | ❌ | **不能** |
| `before_tool` | `reportError` 后**重抛** | ✅ | 能 |

若按原计划实现，会得到一个**看起来生效、实际不生效**的熔断：钩子被调用了、异常被抛了、日志里能看到，但模型照常执行。这比没有熔断更危险 —— 会被当成已经有了，而实际在静默超卖。

所以熔断挂在 `before_tool` 上，用 `{block: {reason}}` 而非抛异常：前者会把理由交给模型，模型能转述给用户（实测模型输出了「本月配额已用尽，请联系管理员提额」）；后者只让任务失败，用户看到一句技术报错。

### 钱不能算错：三条容易写反的实现细节

**① 先汇总再折算，不能逐条折算。**

单条调用几千 token。以 2 元/百万 token 计，一条 3000 token 的调用折合 6 微元。若实现成「每条折算后取整」，累计误差可观；单价更低时每条都会被取整成 0 —— 用户无限用而账上始终是零。

所以 `estimateCost` 先按模型累计 token，最后统一折算并**向上取整**（平台方不该因取整少收）。

**② 金额用整数微元，不用浮点元。**

国产模型 API 单价低到 0.5 元/百万 token。浮点累加几十万条记录会漂移，而漂移方向对平台方不利。

**③ 配额上限用 `!== undefined` 判断，不用真值判断。**

`maxTokens: 0` 的语义是「一个 token 都不许用」（欠费停机），真值判断会把它当成未设置 —— 恰好在最需要拦住的场景下放行。

### 不能漏计：失败任务的消耗照样入账

若任务失败就不计量，用户能靠「发起必然失败的任务」白嫖算力。

Spike 6 确认 `usage` 是**逐轮**上报的、且生成失败前的 usage 不回滚，所以只要在落账路径上不做过滤就行。e2e 里有一条专门验证这个：任务跑一轮后 provider 报错、任务转 FAILED，但账面上有消耗。

落账接线**没有复用**翻译用的那条 `usage` 订阅，因为两者失败语义相反：

| 路径 | 失败后果 | 策略 |
|---|---|---|
| 事件翻译 | 前端少显示一条进度 | 吞异常（已有策略）|
| 用量落账 | 收错钱、账目差异无从追查 | 告警，但不中断执行 |

复用同一条路径会让计量继承「异常被吞」的宽容策略。而「不中断执行」是因为 token 已经烧掉了，中断既救不回钱也白费已完成的工作。

### 安全拒绝优先于配额拒绝

若一次调用同时越权又超配额，用户应当看到「越权」而不是「超配额」—— 越权可能是攻击迹象，被配额理由盖住就查不出来了。

`withQuotaGate` 因此先跑内层安全门，已被拒的调用不再查配额（本来也不会消耗 token）。

### 计量存储故障时默认拦下

静默超支不可回收，而被拦下的任务用户可以重试。私有化部署若本就不限量，应当**把配额设为无限制**，而不是把 `onStoreError` 翻成 `allow` —— 后者会让 SaaS 形态下的计量故障变成免费午餐。

### 变异测试：11 组，1 组逃逸

| 变异 | 后果 | 是否被捕获 |
|---|---|---|
| 漏计 cacheRead | 配额判定系统性偏松 | ❌ **逃逸** → 补测试后被 3 项捕获 |
| `maxTokens` 真值判断 | 0 被当无限制 | ✅ |
| 判定用 `>` 而非 `>=` | 刚好用满时多放行一次 | ✅（6 项）|
| 逐条折算取整 | 小额归零 | ✅ |
| 未配价按免费处理 | 白送算力 | ✅ |
| 存储故障默认放行 | 静默超卖 | ✅（2 项）|
| 配额拒绝盖过安全拒绝 | 越权被掩盖 | ✅ |
| 去掉整条落账接线 | 完全不计费 | ✅（3 项 e2e）|
| 落账失败静默吞掉 | 账目差异无从追查 | ✅ |
| 任务数不去重 | 配额提前触顶，误拦用户 | ✅ |
| 时间窗右端闭合 | 边界双重计费 | ✅ |

**逃逸的那一组值得记录**：把 `totalTokens` 从「input + output + cacheRead + cacheWrite」改成「input + output」后，当时全部 43 项计量测试依然通过 —— 因为只测了 `checkQuota` 这类纯函数，存储的汇总逻辑没有任何断言。

漏计 cacheRead 不会让任何功能出错，只会让平台方少收钱。长对话场景下 cacheRead 可能是输入量的数倍。这类缺陷**没有测试就永远发现不了**，因为它在功能层面完全正常。

补的测试用固定期望值（`1 + 10 + 100 + 1000 = 1111`）而非「大于零」—— 后者在漏掉任一类别时依然通过。

### 当前能力边界

- **拦不住纯文本生成。** 熔断挂在 `before_tool` 上，一次「不调工具、只生成长文本」的运行不经过任何闸门。超限租户提交任务后仍可能烧掉一轮模型调用才被拦下。要在模型调用前拦需改内核（给 `before_request` 加 block 通道）或在 provider 层加闸 —— 前者破坏 vendor 策略，后者留到 M5。
- **配额检查有一轮滞后。** 判定读的是已落账用量，当前这一轮的消耗还没入账。并发任务多时实际超出量可达「并发数 × 单轮消耗」。SaaS 形态应把配额上限设得略低于硬上限来吸收误差。
- **未接入提交前预检。** `evaluateQuota` 已可用，但 `TaskOrchestrator.submit` 还没调它 —— 超限租户仍能提交任务，只是工具会被拦。接入是 M4-3 的事（要同时给用户一条「提交即被拒」的反馈路径）。
- **任务数统计的是有用量记录的任务数**，零消耗的任务不计入。
- **没有周期滚动逻辑。** `Quota.periodStart/End` 由调用方给定，平台不自动推进周期。月度重置需要外部调度。

## M4-2 · 单机 Compose 交付包与自检

验收门禁是「客户 IT 人员 2 小时内独立装成」。达不到这个目标的首要原因**不是安装步骤复杂，而是出错时不知道错在哪** —— 一句 `EADDRINUSE` 或 `fetch failed` 会让客户 IT 打电话，2 小时就没了。

所以这一项的核心产出不是 Compose 文件，而是**两层「说清楚哪里错了」的机制**。

### 第一层：配置校验（启动时）

配置有错就**拒绝启动**，并把**全部问题一次列出**：

```
配置有 2 处问题：
  ✗ MODEL_API_KEY：未配置
      → 在 .env 里填 API Key。内网自建推理服务多数不校验，填任意非空值即可（如 local）
  ✗ PORT：不是整数：80 80
      → 填 1-65535 之间的端口号。1024 以下的端口需要 root 权限
```

三条刻意的设计：

| 决定 | 理由 |
|---|---|
| 不在第一个错误处停下 | 修一个跑一次、再修一个，2 小时预算撑不住几轮 |
| 非法值报错而非退回默认值 | 客户填了 `PORT=80 80` 却发现服务在 8080 上，排查很费时 |
| 建议紧跟问题，不集中到末尾 | 集中在末尾需要来回对照，出错时人没有耐心对照 |

### 第二层：部署自检（`npm run doctor`）

六项检查，每项都回答「失败了该做什么」：

| 检查 | 失败时给的不是 | 而是 |
|---|---|---|
| 端口 | `EADDRINUSE` | `PORT=8081`，或 `lsof -i :8080` 查进程 |
| 磁盘 | 「空间不足」 | `docker system prune -a` |
| 内存 | 「内存不够」 | `MAX_CONCURRENT_TASKS=2`，或扩容 |
| 模型 API | `fetch failed` | 三步排查：出网 → 代理 → 内网地址 |
| 工作区 | `EACCES` | `chown -R 1000:1000 <宿主目录>` |

**`warn` 与 `fail` 分开**是必要的：内存 6GB 能跑但并发一高会 OOM，报成 fail 会让客户以为硬件不达标而放弃采购。

自检脚本真实运行时立刻暴露了一处措辞缺陷：**未配置 `MODEL_BASE_URL` 时却建议「确认服务器能出网、设置 HTTPS_PROXY」**。客户 IT 会去查网络，而实际上只是少填一行配置。**排查方向错了比没有建议更浪费时间。** 已拆成两条独立分支，并补了断言（含 `not.toContain("HTTPS_PROXY")`）。

另一条安全断言：自检输出**绝不回显 API Key**，连长度都不显示 —— 自检报告常被客户 IT 截图发到工作群里。

### 内存探测按 cgroup 而非宿主机

容器里 `os.totalmem()` 报的是宿主机内存，而进程实际能用的是 cgroup 限额。按宿主机判定会让「宿主 64G、容器限 2G」这种常见配置通过自检，然后运行时被 OOM kill。

自检优先读 `/sys/fs/cgroup/memory.max`（v2）与 `memory.limit_in_bytes`（v1），读不到才退回 `totalmem()`。

### 交付包只有一个服务

无外部数据库、无消息队列、无缓存中间件。数据落在挂载卷里。

这是刻意的：每多一个组件就多一处装不上的可能。客户要上规模时再换 Postgres（接口已按可替换设计），但**首次交付不该让客户装数据库**。

### 服务端不引框架

依据是 [Spike 7](../spikes/07-sse-delivery/)：Node 内置 `http` 足够支撑 SSE 与断线重连。手写路由在这个规模（不到十个接口）下比引框架更划算。

Spike 7 查出的真缺陷：**`writeHead()` 不会立即发送响应头**。SSE 场景下若暂时无事件可发，客户端会一直等头 —— 连接建立不起来。生产表现是「任务在跑但前端连不上」，而开发环境往往刚好有事件，这个缺陷不做 spike 就会带到线上。修法是 `flushHeaders()` + 立即写一行心跳注释。

### 真实启动暴露的三处缺陷

**构建通过、767 项测试全绿，但服务一提交任务就失败** —— 这三处只有真的跑起来才暴露：

| 缺陷 | 表现 | 原因 |
|---|---|---|
| 手搓模型对象 | `model_unavailable` | `setProvider` 要完整 `Provider`（含 `getModels()`/`stream()`），不是 `{baseUrl, apiKey}`。应当用 vendor 的 `createProvider` 工厂 |
| 模型缺 `cost` 字段 | `Cannot read properties of undefined (reading 'tiers')` | 内核算 usage 成本时直接读 `model.cost.tiers` |
| 模型名读 `event.row.model` | `"model":"unknown"` | **内核的 usage 事件根本不带模型名** —— `UsageRow` 只有 `{id, seq, usage,...}`，`Usage` 里也没有 |

第三条最值得记：用量事件照常上报、token 数完全正确，只有模型名是 `"unknown"`。而 M4-1 的 `estimateCost` 按模型名查单价 —— **全归到 unknown 等于全部未配价，账面金额恒为 0**。当时 764 项测试全绿，因为**没有一条断言检查过模型名**。

模型名必须由宿主从配置注入。补了 3 项断言后重跑变异，确认能捕获。

**M4-1 那条 `run_end` 订阅在这里救了场** —— 三处缺陷都是通过 `run_end{status:"failed"}` 报出来的。不订阅它的话，任务会被报成 SUCCEEDED 而零产出。

### 边界检查拦下两次越界

写服务入口时两次想直接 import vendor，都被 `check-boundaries.mjs` 拦下：

| 想写的 | 为什么不行 | 改成 |
|---|---|---|
| `import { MemoryStorage } from "vendor/pi/..."` | 会话存储是内核概念 | `MemorySessionFactory`（agent-host）|
| `import { createModels } from "@earendil-works/pi-ai"` | provider 装配是内核细节 | `createModelRuntime`（agent-host）|

拦得对：图省事的那两行会让「将来换掉内核」从改一个包变成改全平台。

### 变异测试

| 变异 | 后果 | 是否被捕获 |
|---|---|---|
| 翻译层退回读 `event.row.model` | 模型名恒 unknown，金额恒 0 | ✅（2 项）|
| 落账用 `"unknown"` | 事件对但账单错 | ✅ |
| input/output 写串 | 账目系统性偏差（输出单价约为输入 4 倍）| ❌ 逃逸 → 改用短问长答后捕获 |
| cacheRead/cacheWrite 写串 | 账目小幅偏差 | ❌ **仍未覆盖**（见下）|

**逃逸的第一组**说明断言太弱：原版只检查「四项都是 number」，而 `fauxAssistantMessage` 的 usage 全是 0 —— 交换 0 和 0 没有差别。改成「短问 + 长回复」让 output 远大于 input 后才能检出。

**第四组仍未覆盖**，这是明确取舍：faux provider 只在同会话第二轮起才产生非零缓存值，为此造场景的成本高于收益（两项单价接近）。已在测试文件里写明，接入按缓存计费差异大的模型时要补。

### 当前能力边界

**写在 deploy/README.md 里给客户看，不藏起来**：

- **鉴权是单租户退化形态。** 任何非空 token 映射到同一个默认租户。这不是「鉴权没做」而是单机私有化部署下的够用形态，但**不能用于多部门隔离或对外服务**。M5 接真实账号体系。
- **会话与计量都在内存里**，进程重启后丢失。重启会让进行中的任务失去上下文、用量归零（配额随之失效）。M5 落盘。
- **无前端界面**，目前只有 HTTP API。
- **无管理后台**（M4-3）。
- **Dockerfile 未在真实 Docker 环境验证过** —— 当前环境没有 Docker daemon。配置本身经过评审（两阶段构建、非 root、资源上限、日志轮转、healthcheck 走自检脚本），但首次交付前必须在真机上跑一遍 `docker compose up`。
