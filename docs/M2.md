# M2 交付说明

多租户与场景化。核心交付物是**场景卡**——用填表替代空白输入框，这是让目标用户真正用起来的前提。

## 怎么跑

```bash
npm run verify          # 边界检查 + 全部自有测试 + M0 spike
npm test                # 443 项自有测试（含 e2e）
npm run spike           # 22 项 M0 验证
```

## 验收标准与实际达成

需求 §6 的 M2 验收标准：**任一场景卡可在不输入自由文本 prompt 的前提下完成任务提交。**

[e2e/scenario-card-flow.test.ts](../e2e/scenario-card-flow.test.ts) 逐条验证，且**全文没有一句手写 prompt**——指令全部由 `compilePrompt()` 从场景卡模板 + 表单值编译而来。

这里需要把「不输入自由文本 prompt」的口径说清楚，否则容易变成自欺：

- 用户**仍然要填业务内容**（客户投诉了什么、要通知什么事）。这是数据录入，是他们每天在做的事，不是 prompt 工程。Agent 不可能猜出客户的投诉内容。
- 用户**不需要写任何指令**：产出该有哪些栏目、按什么标准组织、数据缺失时怎么办，全部由场景卡的 `systemPrompt` 与 `promptTemplate` 提供。

## 本阶段查出的两个缺陷

### 1. 内核运行失败被报成任务成功（严重）

写 M2 e2e 时发现：给 `activeTools` 传入一个未注册的工具名，任务状态是 `SUCCEEDED`，但**模型一次都没被调用、零产出**。

根因：内核把生成阶段的失败（模型不可用、`activeToolNames` 含未注册工具、provider 报错）通过 `run_end{status:"failed"}` 事件上报，而 `lane.prompt()` **正常 resolve**。适配层只接了 `tool_start`/`tool_update`/`tool_end`/`usage` 四个事件，漏了 `run_end`。

用户视角的后果：界面显示「已完成」，但产出目录里什么都没有，日志里也看不出异常。这类缺陷在生产环境几乎无法定位。

修复分两层：
- 适配层接 `run_end`，失败时让 `prompt()` 抛错，由编排层转入 `FAILED`
- `createRunner` 在创建阶段就校验 `activeTools ⊆ 已注册工具`，报错信息指出是哪个名字不对——放到内核里报只能拿到一句「任务失败」

三个变异测试确认这组断言有效（去掉失败检查 / 去掉 `run_end` 接线 / 不清空上次失败原因，各自都被测出）。

### 2. 场景卡设计先于工具实现的处理方式

10 张卡里 8 张声明了 M3 才实现的工具。原样传给内核会让**整张卡完全不可用**（生成阶段直接失败）。

处理方式是 `activateableTools()` 取交集：卡片能跑通它已有工具支持的那部分，缺的工具只是能力受限。这样 M3 补工具是纯增量改动，无需回头改场景卡定义。

刻意**没有**在适配层做「静默忽略未知工具名」的宽容处理——那会让「场景卡写错工具名」变成查不出的能力缺失。需要容忍时由调用方显式取交集。

## 场景卡的结构性校验

场景卡是数据而非代码，写错不会编译失败。[preset-cards.test.ts](../packages/core/test/preset-cards.test.ts) 对每张卡逐项断言：

| 检查项 | 防的是什么 |
|---|---|
| 每个字段都被模板引用 | 用户认真填完、系统静默丢弃 |
| 模板引用的字段都有定义 | 指令里出现字面量 `{{xxx}}`，模型当成待填内容 |
| 默认值必须合法 | 用户什么都不改直接提交就被拦住 |
| 文件字段必须限制格式 | 上传 .zip 一路走到工具层才失败 |
| 选项类字段必须有选项 | 前端渲染出空下拉框 |
| 声明的工具都在目录里登记 | 工具名打错 → 白名单静默失效 |
| 没有 bash 等自由命令执行 | 场景卡是最容易偷偷开口子的地方 |
| systemPrompt 含防幻觉约束 | 编造数据的代价是审核不符合项甚至丢标 |
| 至少一个必需字段 | 空提交也能过，Agent 只能瞎猜 |

测试用例由卡片元数据**自动推导**而非手写 10 组样例：前端渲染表单靠的就是这些元数据，如果测试推不出合法值，前端也渲染不出可用的表单。

## 两层工具白名单

| 层 | 机制 | 作用 |
|---|---|---|
| 模型侧 | `activeToolNames` | 工具在模型的 transcript 里根本不出现 |
| 执行侧 | `restrictPolicies()` + 权限门默认拒绝 | 模型若强行调用（越狱、上下文污染、内核缺陷）仍被拦下 |

e2e 里两层各有正反验证：断言模型侧 transcript 确实看不到核对工具；以及模型强行调用未激活工具时，产物不存在且审计记了 `blocked`。

模型侧的断言刻意读**模型实际收到的 transcript**，而不是检查我们传进去的参数——后者只证明我们的意图，不证明内核照做了。

## 能力边界（不含糊）

- **检索是关键词而非向量。** 行业用户的查询多是明确名词，关键词召回够用；向量检索需要 embedding 服务，私有化部署时又是一个外部依赖。二期按需引入时实现同一个 `Retriever` 接口即可。
- **文档与知识库工具已在 M3-1/M3-2 补齐**，十张场景卡现已全部可跑到产出。
- **溯源记录需由调用方主动构建。** `ProvenanceBuilder` 提供了能力，但工具内部尚未自动登记数据项级来源——M3 随文档工具一起接。
- **多租户是模型与校验层面的，尚无持久化。** 租户隔离的判定逻辑与测试已完备，但存储层仍是内存实现。
