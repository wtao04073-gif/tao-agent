## M3-1 · 文档读写工具

### 场景卡可跑到产出的数量：2 → 6

| 场景 | 变化 |
|---|---|
| 生成 8D 报告 | ⏳ → ✅ |
| 整理安全检查记录 | ⏳ → ✅ |
| 生成生产日报周报 | ⏳ → ✅ |
| 整理整改台账 | ⏳ → ✅ |

剩余 4 张（体系文件、评估自评报告、通知公文、项目申报书）只缺 `search_knowledge`，已在 M3-2 补齐——**十张卡现已全部可跑到产出**。

### 先做探针再写实现

动工前先做了 [Spike 4](../spikes/04-docx-fidelity/docx.spike.ts)（8/8 通过），验证 `docx`（写）+ `mammoth`（读）的组合能保住标题层级、表格、中文与行内格式。

理由与 M1 做 xlsx 时相同：产出要能直接提交客户或专家组，如果结构在生成后退化，整条链路就是废的——而这**只有真跑一遍才知道**。M1 那次探针发现了「公式必须用 `{formula}` 对象否则退化为纯文本」，省掉后面一堆返工。

### 关键设计：模型提交结构化文档树，而非 Markdown

`write_document` 的参数是[结构化块序列](../packages/office/src/doc-model.ts)（标题、段落、列表、表格、分页），不是 Markdown 字符串。

这个取舍的理由：

- **Markdown 表达不了审核材料需要的东西**——合并单元格、表格列宽、字体要求（体系文件常规定「正文宋体小四」）。
- **让模型写 Markdown 再由我们解析，等于把「格式是否正确」变成解析器的猜测。** 结构化参数经 JSON Schema 校验，写错直接报错，不会静默产出一份格式错乱的文件。
- **结构化之后每个块有稳定身份**，溯源才能定位到「哪一段」。

代价是 schema 较长，模型要照着构造。但 schema 含糊的直接后果是模型随意发挥、产出格式每次都不一样——对「同类任务产出要能收敛」这个目标是致命的。

### 「待补充」占位会被高亮

场景卡的 systemPrompt 要求模型对信息不足处标注「待补充」而非编造。那么这些位置在产出里必须**显眼**：

- `InlineRun.placeholder` 为真时渲染成黄色高亮加粗
- 工具回复里点出「有 N 处标为待补充，请补齐后再对外提交」

否则用户会连着占位符一起交给审核方——这比编造数据的后果只轻一点。

### 读取端按段落返回并带序号

`read_document` 返回的是**带序号的段落列表**，不是一整块文本。两个理由：

1. **溯源要能定位到「哪一段」。** 审核员指着自评报告某段问「这句话依据是什么」，系统要能答出「来自 XX制度.docx 第 12 段」。
2. **上下文预算。** 评估指标文件动辄几十页，整篇塞进上下文会挤掉真正要处理的数据。单次最多返回 40 段，并明确告知还剩多少。

配套的 `outlineOnly` 先取标题骨架——处理评估指标体系、申报指南这类长文档时，先了解结构再逐项取内容，比一次读全文省得多。

### 实现阶段暴露的一个缺陷（探针没覆盖到）

mammoth 转出的 HTML 去掉标签后，**表格单元格与列表项会无分隔符粘连**：

```
序号问题描述责任部门完成期限
1部分课程大纲未及时更新教务处2026-12-31
```

模型读到这种文本无法还原列边界，处理台账时必然串列。修复方式是在去标签前按 `<tr>`/`<td>`/`<li>` 切分并插入 `|` 分隔符，列表的每个条目单独成段。

这说明探针的边界：它验证了「库能用」，但「用对」仍需实现阶段的测试兜住。该缺陷是被 round-trip 断言抓到的——**写进去再读回来对比**，而不是只验「文件存在」。

### 安全边界

| 约束 | 实现方式 |
|---|---|
| `outputName` 只能是文件名 | `writeDocx` 拒绝含 `/`、`\` 或绝对路径的名字 |
| 产物一律落在工作区 | 路径由 `join(workspace, outputName)` 拼出，不接受模型指定目录 |
| 读取路径经权限门校验 | `DOC_TOOL_POLICIES` 登记 `read_document` 的 `path` 参数 |

`write_document` 刻意**不登记路径参数**——因为它没有路径参数可言，产出位置完全由平台决定。给模型指定输出路径的机会等于绕过路径策略。

两条安全断言都做了变异测试：去掉系统路径检查、去掉路径参数登记，各自都被 e2e 测出。

### 产出后必校验

与 xlsx 一致：[validateDocx](../packages/office/src/validate-docx.ts) 验证文件能被重新解析、结构完整、标题与表格未退化。写出去一份 Word 打不开的文件，用户会当着客户或专家组的面发现。

能力边界同样说清楚：能验证**文件可解析、结构完整**；不能验证「在 WPS 里肉眼看着对不对」——那需要真实 Office 环境，属于交付前人工抽检。

### 当前能力边界

- **只支持 docx，不支持 doc。** 老格式（Word 97-2003）需要额外的转换链路。高校与制造业仍有存量 .doc 文件，这是个真实缺口，但优先级低于 `search_knowledge`。
- **不支持读取 docx 里的图片与嵌入对象。** 检验报告的现场照片、工艺图纸目前读不到，场景卡里这些字段接受图片上传但 Agent 看不见内容。
- **不保留源文档样式。** 「修订已有文件」场景目前是读内容 + 重新生成，不是在原文件上改——格式会变成我们的模板样式。这在 M3-4 模板资产落地后才能解决。
- **溯源尚未自动登记。** `read_document` 返回了段落序号（溯源需要的 locator），但工具内部还没把它写进 `ProvenanceBuilder`。

## M3-2 · 知识库检索与入库

### 场景卡可跑到产出的数量：6 → 10（全部）

补齐的 4 张都依赖「引用本单位已有材料」：编写体系文件、撰写评估自评报告、起草通知公文、整理项目申报书。这正是通用 Chatbot 做不到的事——它不记住本单位的口径、模板与制度，每次都要重新喂上下文。

### 切分是检索质量的真正瓶颈

切分策略按**标题边界**而非固定字数。目标客户的文档有两个特点决定了这一点：

1. **强层级结构。** 体系文件、评估指标、管理办法都是「第X章 / 第Y条」的树形结构。按固定字数切会把「5.2 不合格品处置」的标题与正文切开，检索命中标题却拿不到内容。
2. **条款是自然的检索单位。** 用户查「不合格品怎么处置」，要的是那一条的完整内容，不是横跨两条的一段文本。

每个片段带**标题路径**（「质量手册 > 第5章 > 5.2 不合格品处置」），并把路径拼进正文参与匹配——用户常用标题词检索，而这些词往往不在条款正文里。

两个容易写错的细节，都由测试锁住：
- **同级标题替换而非累积**：5.2 的路径里不能还带着 5.1
- **标题处不保留上一条的重叠内容**：否则检索结果会显示错误的出处（命中 5.2 却标成 5.1）

### 身份不从模型参数取

`search_knowledge` 的身份来自平台在装配工具时注入的 `membership`，工具的 `parameters` schema 里**根本没有租户字段**。

这是整个设计的要害。若让模型传租户 id，越狱提示或上下文污染就能让它读别家知识库——而这种泄漏极隐蔽：产出看起来正常，只是内容里混进了别家的数据。

测试里专门验了「模型硬塞 `tenantId` 和 `membership` 参数」的情况：不仅召回为空，还断言 schema 的字段列表精确等于 `["query", "limit", "knowledgeBaseIds"]`，确认这些字段不是「被接受但忽略」，而是根本不存在。

### 跨租户不删除——较少被想到的那一面

删除片段时必须同时匹配 `tenantId`。只按 `documentId` 删会让 A 租户删掉 B 租户的同名文档——`documentId` 若来自文件名或用户输入，这就是个真实可利用的**跨租户写入**漏洞。

### 文档更新时先删后加

`ingestIntoStore` 先 `removeDocument` 再 `add`。不删的话新旧两版会同时被召回，用户拿到自相矛盾的引用却不知道原因。

### 无命中时明确提示，不返回空串

返回空字符串会让模型自行想象制度内容——这是最危险的幻觉场景：编造出来的「制度规定」会被用户当真写进正式公文，发出去才发现本单位没有这条规定。

所以无命中时的回复是：「知识库中未找到…如需引用制度或模板，请告知用户知识库缺少相关材料，**不要凭记忆编写**。」

### 修正了一条假通过的断言（两次）

原本写「只在标题里的词也能检索到」。变异测试暴露它是假通过，根因是 `tokenize` 对**中文按单字切分**：「内部审核」拆成 内/部/审/核，而正文「内审每年…覆盖全部过程」本身就含 内/审/部，所以不拼标题也能部分命中。

**按字切分让「某个词只出现在标题里」这个概念在中文里几乎不成立。** 这是检索设计的一个真实局限，已记录在 [retrieval.ts](../packages/core/src/retrieval.ts) 的 `tokenize` 注释里：相关度是渐变的，没有「完全不匹配」的清晰边界。

第二次修正是构造方式：改成比较两组分数后**仍然**假通过，因为对照组也用 `toChunks` 构造，变异后两组同时退化。最终改用固定期望值（拼标题后分数应 > 0.8，不拼时约 0.43）。

这个过程本身是个教训：**对照组不能依赖被测代码**，否则变异会让两边一起变，差异消失。

### 为什么现在不做持久化

`KnowledgeStore` 抽成接口，一期是内存实现。检索的正确性瓶颈是切分与权限过滤，这两件事与存储介质无关。先把接口定死、权限测试写全，换存储时只需实现同一个接口，测试可直接复用。

私有化部署的单机形态用内存实现就够——一个租户的制度文件通常几百到几千个片段。

### 当前能力边界

- **入库不作为工具暴露给模型。** 入库是管理动作，由用户在知识库管理界面上传文档触发，不该由 Agent 在任务执行中自行决定往知识库里写东西。
- **检索是关键词而非向量。** 中文按字切分的局限见上。二期引入向量检索时实现同一个 `Retriever` 接口即可。
- **无持久化。** 重启后知识库为空，需重新入库。
- **溯源仍需调用方主动构建。** e2e 里演示了怎么把检索命中登记进 `ProvenanceBuilder`，但工具内部还没自动做——`details.citations` 已备好数据，等 M3-3 一起接。
- **只支持 docx 入库。** pdf 与 xlsx 的制度文件目前进不了知识库，这是个真实缺口：上级下发的评估指标文件常是 pdf。

## M3-3 · 修改意见回写（M3 验收门禁）

### 验收标准怎么验才不算自欺

需求 §6 原文：**同类任务第二次产出不再犯上次被改的错。**

这条标准有三种验法，前两种都是自欺：

| 验法 | 问题 |
|---|---|
| ❌ 断言「经验被注入了」 | 测的是字符串拼接，不是经验起作用 |
| ❌ 假模型硬编码第二次的正确产出 | 测试自己在作弊 |
| ✅ 假模型**按实际收到的 system prompt 决定产出** | 「经验起作用」成为可观测的因果关系 |

[e2e/lesson-feedback.test.ts](../e2e/lesson-feedback.test.ts) 用第三种：假模型的响应函数读取真实收到的系统提示，若经验没被注入就产出旧写法。再用 `findRepeatedMistakes` 对两次产出做客观判定。

配套的**反向对照组**同样重要：刻意不注入经验，验证模型仍犯旧错且被检出。没有它，正向用例可能只是「假模型恰好产出了正确内容」。

### 核心取舍：用户不会写经验条目

用户只会**直接改产出**——把「负责人」改成「责任部门」、删掉一整段、改掉日期格式。所以系统必须从修改动作本身提取经验，而不是指望用户填「请总结你的偏好」表单。

但从 diff 自动推断意图不可靠：改了个字可能是笔误，也可能是口径纠正。所以是两者结合：

1. 系统记录客观事实（哪个位置被改了、改成什么）
2. 用户**可选地**补一句为什么（「我们一律用责任部门」）
3. 注入时把事实与理由都给模型，让它自己判断如何应用

### 刻意不做自动泛化

「用户改了一次日期格式」不等于「所有日期都要这样」。过度泛化的经验比没有经验更糟——它让产出朝用户没要求的方向漂移，而用户无法理解为什么。

泛化由**重复次数**驱动：同一条被改过多次才提升权重，注入时高权重优先并标注「已重复 N 次」。改一次是偶然，改三次就是口径。

### 注入措辞：历史偏好而非硬性规则

注入的文本明确说「这些是历史偏好而非硬性规则。若本次任务的实际情况与之冲突，以本次要求为准」。

断言式规则会让模型在不适用的场合硬套，产出反而变差。我们只观察到几次修改，还不知道它是否普适。

### 为什么不用通用 diff 算法

通用 diff 给的是行级增删，我们需要的是**语义级修改**：「『负责人』这一列改成了『责任部门』」而不是「第 3 行删除、新增第 3 行」。

所以按产物结构对齐：文档按段落锚点，表格按表头与行键。锚点对齐的好处是**中间插入一段不会让后续所有段落都被判为改过**——否则会沉淀出一堆假经验。

### 写测试时查出的一个真实缺陷

原实现只看改动比例来判断「用户是重写而非修订」。但**比例在小样本上不可靠**：一份 3 段的公文改掉 2 段（0.67 > 0.6）会被判为重写而放弃学习——而那正是最典型的正常修订场景。

等于让整条回写链路在最常见的情况下失效。修复是加最小样本量门槛（`MIN_ITEMS_FOR_RATIO = 6`），样本不足时一律提取。

### 两次被变异测试逼出的测试修正

**第一次**：断言「按重复次数降序」曾假通过。`MemoryLessonStore.list` 已按权重排好序，所以即使 `compileLessons` 完全不排序也能通过——**双重排序掩盖了缺陷**。换一个不排序的 store 实现就会暴露。修正为直接喂升序输入。

**第二次**（e2e）：假模型的检测标记原本用「责任部门」，但场景卡的 systemPrompt 里本来就含这个词（「责任部门无法判断的标注待分工」），导致未注入的情况被误判为已注入。反向验证用例把它暴露了出来——**这正是反向对照组的价值**。改用 `compileLessons` 的固定开头「历史修改记录」作标记。

### 隔离

| 维度 | 理由 |
|---|---|
| 按租户隔离 | 别家的口径绝不能影响我方产出 |
| 按场景隔离 | 台账的「负责人→责任部门」不该影响 8D 报告（那里「小组负责人」是正常措辞）|

两条都有 e2e 验证。跨租户删除也验了——用户不能删掉别家的经验。

### 本项模块

## M3-4 · 模板与口径资产

### 解决两个具体问题

1. **格式不稳定。** 同一类公文每次产出版式都不一样，用户要反复调。体系文件、公文、台账在每个单位都有固定格式，这不是模型能猜到的。
2. **字段口径不一致。** 「在校生数」含不含留学生、休学生？高校「一张表工程」的核心痛点就是各部门口径不同，汇总永远对不上。

### 四类资产的边界

容易混淆，必须说清：

| 资产 | 回答什么问题 | 谁定义 | 性质 |
|---|---|---|---|
| 场景卡 | 这类任务要收集哪些输入、产出什么 | 平台预置，租户可覆盖 | 规范 |
| **模板** | 产出长什么样（章节、栏目、版式） | 租户维护 | 规范 |
| **口径** | 某个字段/指标怎么算 | 租户维护 | 规范 |
| 经验 | 上次哪里被改了 | 系统从修改中学习 | 推测 |

模板是**用户主动提供的规范**，经验是**系统被动学到的偏好**。前者权威稳定，后者是推测。所以注入顺序是模板 → 口径 → 经验，且**冲突时的优先级显式写进注入文本**——否则模型面对矛盾指令时行为不可预测。

措辞也相应不同：模板用命令式（「必须包含」「缺少任一项会被审核退回」），经验用「上次被改为」。

### 模板存结构化定义，不存原始文件

刻意不存用户上传的 docx，而是存章节/列定义。理由：

- 存文件只能「照着改」，无法让模型理解「这里该写什么」
- 结构化定义可以**校验产出是否合规**（缺了哪个必需章节）
- 样式细节由 `layout` 承载即可

代价是用户上传 docx 后需要一步「解析成模板」的动作，可半自动（从标题层级提取）+ 人工确认。

### 合规校验必须容忍编号风格差异

这是最容易做错的地方。模板写「1 目的」，产出可能是「一、目的」或「1. 目的」——**用精确匹配会让所有产出都被判为缺章节，功能等于废掉**。

实现是剥掉标题前的编号字符再做包含匹配。变异测试确认这条断言有效：改成精确相等后立刻失败。

另一个取舍：**多出来的列是警告而非错误**。本次任务可能确实需要额外信息，判为不合规会让用户无法添加临时栏目。

### 口径只注入本次相关的

全部注入会让上下文塞满几十条无关口径，真正相关的反被淹没。`compileDefinitions` 接受一个 `relevantTo` 参数按任务内容过滤。

口径定义里 **`excludes` 比 `includes` 更重要**——争议都在边界上。「在校生数不含休学学生」这句话才是消除分歧的关键。同时记录口径负责部门，出现分歧时知道找谁。

|---|---|
| [assets.ts](../packages/core/src/assets.ts) | 模板与口径模型、注入编译、合规校验、优先级合成 |
| [memory-asset-store.ts](../packages/knowledge/src/memory-asset-store.ts) | 资产存储，按租户分桶 |

### 测试

- [packages/knowledge/test/assets.test.ts](../packages/knowledge/test/assets.test.ts) —— 33 项
- [e2e/asset-template.test.ts](../e2e/asset-template.test.ts) —— 5 项端到端
- 6 组变异测试确认断言有效（编号容忍、多余列为警告、优先级声明、口径过滤、模板优先级、租户隔离）

e2e 与 M3-3 同一思路：让假模型按**实际收到的上下文**决定产出，而非硬编码正确答案。没收到模板就只写三章，收到才写全五章。

### 当前能力边界

- **不保留源文档样式。** M3-1 遗留的「修订已有文件会丢格式」只解决了一半：模板能让产出符合本单位版式，但仍是**重新生成**而非在原文件上改。真正的原位修订需要操作 docx 的 XML，留到后续。
- **模板解析未实现。** 用户上传 docx 后自动提取章节结构的功能还没做，目前需手工录入模板定义。这是管理后台的工作，排在 M4。
- **口径匹配是字面包含。** `compileDefinitions` 用 `relevantTo.includes(name)` 判断相关性。字段名的同义表述（「学生数」vs「在校生数」）匹配不到。
- **合规校验只查章节与列的有无。** 不校验内容是否真的符合该章节的要求——那需要模型判断，属于产出质量评估范畴。
- **资产无版本管理。** 模板改了之后，用旧模板产出的历史文件无法追溯当时的模板版本。溯源记录里有 `SourceKind.Template`，但尚未接上。

## M3-5 · 子 Agent 并行

### 先做 spike，结果推翻了 M0 的一处结论

M0 Spike 1 的结论写的是「同一 Session 下的多个 lane 在 mutation line 上**串行执行**」。[Spike 5](../spikes/05-subagent-parallel/) 实测发现这个表述过强。

准确的事实：`MutationLine` 只串行化**存储的读-改-写**，不串行化模型调用。

实测数据（两个各 60ms 的子任务并发发起）：

| 形态 | 总耗时 | 模型调用时序 |
|---|---|---|
| 同 Session 两个 lane | 73ms | A-start, B-start, A-end, B-end（交错）|
| 两个独立 Session | 62ms | 同样交错 |
| （完全串行会是）| 120ms | — |

这个区别直接影响设计：若真是串行，一子任务一 Session 是**必须**；实际是约 18% 的写入争用开销，所以它是**优化选择**。

**仍然采用它，但理由换了**：
- 写入争用随子任务数放大
- 故障隔离：一个子任务的存储损坏不影响其他
- 独立检查点：子任务可单独续跑

M0 的表述已在 [spikes/README.md](../spikes/README.md) 就地修正。**错误的事实判断即使得出了正确的决策，也必须改**——否则下一次基于它做决策时会出错。

### 一条硬约束：并发上限

不设上限的扇出是生产事故来源：10 个部门的数据汇总同时拉起 10 个模型请求，撞上 provider 速率限制后全部失败——比串行慢得多。

默认上限取 3，保守。国产模型 API 的速率限制通常按每分钟请求数计，而一个子任务可能发起多轮调用。私有化部署用自有推理服务时可调高。

### 三条容易写错的语义

| 语义 | 写错的后果 |
|---|---|
| 一个失败不中断其他 | 某部门文件坏了导致全部结果丢失。用户宁可拿 9 个结果加一条错误 |
| 结果按**输入顺序**而非完成顺序 | 扇出后不知道哪个结果对应哪个子任务。用 push 收集就会得到完成顺序 |
| 进度上报失败不影响执行 | 前端一个渲染错误炸掉整个扇出 |

第三条是写测试时查出的真实缺陷——原实现没有 try/catch，回调抛异常会让整个 `fanOut` 失败。

### 变异测试暴露的一个弱断言

`maxConcurrency: 0` 这个非法配置，原本只断言「返回 3 条结果」。但 `Array.from({length: 0})` 产生零个 worker，`Promise.all([])` 立即 resolve，兜底逻辑把全部子任务标成 failed——**结果条数对了，实际一个都没跑**。

这比死锁更隐蔽：不报错、不卡住、只是静默什么都不做。断言加强为验证 `run` 真的被调用了 N 次。

### e2e 里查出的另一个判断缺陷

`runSubTask` 原本用「`prompt()` 没抛错」判定成功。但工具报错（文件不存在）时，内核把错误返给模型让它重试，`prompt()` **正常 resolve**——这是内核的正确行为。

所以「没抛错」只说明流程走完了，不说明产出了东西。在扇出场景里这个区别很致命：某个部门的文件坏了却报成功，用户拿着缺一份数据的汇总去交付。改为按**产物是否真的存在**判定。

### 时序断言不该变成机器性能断言

第一版用总耗时判定并行（`elapsed < 110ms`），在含 xlsx 读写的 e2e 里失败了（126ms）。总耗时包含 IO 开销，阈值实际上在断言机器性能。

改为记录各子任务的模型调用时间窗，验证三者有共同的重叠区间——直接反映「三个调用同时在飞」这件事，不受 IO 影响。

### 当前能力边界

- **拆解由调用方决定。** `fanOut` 只负责并行执行，不负责「把一个任务拆成几个子任务」。让模型自己决定拆几个子任务需要额外的工具与约束，留到后续。
- **子任务不能再扇出。** 没有嵌套并发控制，二级扇出会让并发上限失效。
- **无跨子任务的共享上下文。** 每个子任务独立会话，看不到其他子任务的中间结果。需要共享时得由父任务先汇总再分发。
- **未接入任务编排器。** `TaskOrchestrator` 还不知道子任务的存在，父任务的状态机没有「部分成功」这个状态。这是接入编排层时要补的。
