# 需求 Spec：行业通用 AI 办公 Agent 平台

---

## 1. 背景与目标

### 需求来源

业务驱动。高校服务机构与传统制造业的办公岗位承担大量结构化、重复、有硬截止日期的文档与表格工作，但现有工具供给存在断层：

- 通用 Chatbot（网页版）**不记住本单位的口径、模板与历史修改意见**，每次都要重新喂上下文，且无法处理本地多表交叉核对、无法产出可直接流转的交付物；
- Claude Code 这类 Agent 产品能力足够，但形态面向开发者（终端 / IDE），行业用户的能力画像与之完全错配；
- 私有化 Agent 平台（Dify / FastGPT 等）是「平台」而非「办公工具」，需要客户自己搭建应用，而这两类客户恰恰没有这个能力。

平台侧选用 Pi 作为 Agent 内核。Pi 是 MIT 协议的极简 coding agent harness（现由 Earendil 维护），仅内置 read / write / edit / bash 四个工具与不到 1000 token 的系统提示，设计哲学是「原语而非功能」—— 刻意不提供 subagent、MCP、权限弹窗、plan mode、内置待办等能力，全部交由扩展实现。它提供的可靠原语包括：多提供方模型统一接入层（15+ 提供方，支持会话中途热切换模型）、树状可分叉的会话历史、按需加载的技能机制、中途插话与排队追问（steering），以及 SDK 与 RPC 两种嵌入方式。

**本产品的工程边界因此是清晰的**：Pi 只覆盖最内层的 Agent 运行时；多租户与权限、异步任务编排、知识资产沉淀、场景工作台、Office 产出、计量计费、管理后台、多端前端、私有化交付这些层全部需要自建。这一分工与「不与通用 Agent 拼功能、把差异化压在行业深度与交付形态上」的定位是一致的。

### 业务目标

1. **让行业用户以低门槛获得接近 Claude Code 的 Agent 执行能力**——能调工具、能读知识库、能派子 Agent 并行、能异步执行长任务，但交互形态适配「不会写 prompt」的办公用户。
2. **成为客户机构的办公知识资产沉淀载体**——把模板、字段口径、审核修改意见结构化留存并自动复用，解决通用 Chatbot「不学习、不记忆」的结构性缺陷。
3. **双形态覆盖两类采购习惯**——Docker 私有化交付满足数据不出门与信创合规要求；SaaS 形态支撑低门槛试用与中小客户。

### 成功指标

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 首周产出率 | ≥ 60% | 新开通账号在首周内产出至少一份可交付物（docx/xlsx/pptx）的占比。对抗「买了没人用」的首要指标 |
| 席位周活率 | ≥ 40% | 已开通席位的周活跃比例。行业基线是大量 AI 工具上线后沦为闲置 |
| 单份材料人工耗时降幅 | ≥ 50% | 以客户侧实测对比为准（参照可比案例：某企业把标准嵌入工作流后审核时间从 8 小时压缩到 3 小时） |
| 私有化安装耗时 | < 2 小时 | 由客户自有 IT 人员（非专业运维、不懂容器编排）独立完成 |
| 交付物格式保真率 | ≥ 95% | 生成的 Office 文件在 Microsoft Office 与 WPS 中打开后版式无错乱。这是直接对手的公开短板 |
| 单租户模型成本 | ≤ 10 元/人/月 | 100 人规模机构的常规办公使用量下 |

## 2. 用户与场景

### 目标用户

**用户群 A：高校服务机构人员**

行政、教务、科研管理、学生工作、资产后勤等岗位的专职管理人员（非教学一线）。特征：

- 工作产出以「材料」为单位——通知公文、统计报表、评审材料、申报书、评估自评报告、整改台账、会议纪要；
- 数据分散在多个部门自建系统，重复填表是被官方与业界共同确认的第一痛点，已形成「一张表工程」这一治理概念与采购话语体系；
- 所在单位信息化部门人力结构性不足（编制收紧、AI 技能断层明显），无法承担复杂运维或二次开发。

**用户群 B：传统制造业办公与管理岗**

中小型制造企业的质量、工艺、生产管理、采购、安全等管理岗位。特征：

- 工作产出为体系文件与质量文档——生产日报周报、质量分析（8D 报告）、工艺文件与 SOP、供应商对账、设备台账、ISO9001/IATF16949 体系文件、安全检查记录、培训材料；
- 长期处于「纸质表单 → Excel → 逐条录入系统」的手工链路，多表口径不一致、跨表核对靠人工；
- 付费动机是**通过审核与客户验厂**（体系认证不通过意味着丢订单），而非单纯效率提升；
- IT 团队规模极小（10 亿营收以下企业普遍 ≤10 人），图纸、工艺、配方为核心机密，要求不出厂。

**两类用户的共性能力画像（决定产品形态的关键约束）**

- 会把 AI 当搜索引擎使用，但**不会写有效 prompt，更不会写 Agent 指令**；
- 对「看起来很强但用不起来」的企业 AI 工具有明确抵触——因为他们在个人场景里体验过好用的 AI，容忍度更低；
- 组织侧普遍缺乏 AI 培训供给，采纳需要产品自带机制而非依赖客户培训。

### 核心场景

**场景 1：高校——评估检查材料生成与填报（首期重点）**

周期性脉冲需求，有硬截止日期。用户接到上级评估或检查通知后，需在限期内产出一整套材料（自评报告、过程性与结果性数据报告、整改方案、整改台账）。当前做法是从多个系统导出数据、人工核对、按模板逐份撰写。

**场景 2：制造业——体系文件与质量报告（首期重点）**

客户验厂或第三方审核前的集中准备，以及日常的 8D 报告、内审检查表产出。痛点在于同一套事实要按不同标准（ISO9001 / IATF16949 / 客户特殊要求）维护多份文档，口径不一致会被开具不符合项。

**场景 3：日常通用办公（底座能力，全程可用）**

写改文档、做表格、统计与核对数据、写 PPT、联网搜索、知识问答、事项规划。单次任务价值不高但频次最高，是维持席位活跃度的基础。

## 3. 功能需求

### 3.1 场景工作台（主入口）

- **功能描述**：以场景任务卡为首页主入口，替代空白对话框。卡片按行业与职能分组（如「生成 8D 报告」「整理评估整改台账」「多表数据核对」「起草通知公文」）。用户选择场景后进入引导式要点收集，系统在此过程中把用户输入映射为内部执行指令。
- **业务规则**：
  - 每个场景卡定义了必需输入（材料 / 数据源 / 关键参数）与可选输入，必需输入未齐备时不允许提交执行；
  - 场景卡分平台预置与租户自建两类，租户自建可覆盖同名平台场景；
  - 保留自由对话入口，供追加诉求与场景外任务使用。
- **输入/输出**：输入为场景选择 + 引导表单 + 附件；输出为任务创建成功并进入执行态。

### 3.2 Agent 执行引擎

- **功能描述**：基于 Agent Loop 的任务执行核心，具备思考 → 选工具 → 行动 → 观察的闭环能力。支持主 Agent 拆解任务并派发子 Agent 并行执行，子 Agent 间上下文隔离、结果汇总、失败可回退。
  > 子 Agent 并行能力**需以扩展形式自建**——Pi 内核刻意不内置该能力，官方给出的路径是扩展、第三方包或多实例。这是本模块的主要工程量来源之一。
- **业务规则**：
  - 任务执行过程对用户可见（步骤级进度、当前动作、已产出中间物）；
  - 工具调用遵循默认拒绝 + 白名单放行；高危动作（对外发送、批量修改、删除）必须人工确认后执行；
  - 单任务执行有步数与时长上限，超限转为需用户确认是否继续。
- **输入/输出**：输入为结构化任务指令与上下文；输出为交付物文件 + 执行日志。

### 3.3 异步任务与并行会话

- **功能描述**：任务是与会话解耦的一等公民。任务提交后异步执行，用户可立即在同一会话或新会话中进行其他问答，不被阻塞。任务进度以事件流回投到来源会话，同时在任务中心统一管理。
- **业务规则**：
  - 任务具备独立标识与持久化状态，支持检查点续跑——执行节点异常重启后从检查点接力，不重复消耗已完成步骤；
  - 任务状态包含：排队中、执行中、等待确认、已完成、失败、已取消；
  - 任务支持取消与重试；失败任务保留已产出的中间物与失败原因；
  - 并发任务数按套餐档位限制（免费/基础档有排队上限，高档位放开）。
- **输入/输出**：输入为任务提交；输出为任务标识 + 实时进度事件 + 最终产物。

### 3.4 机构知识资产（核心差异化能力）

- **功能描述**：三类资产的沉淀与自动复用：
  1. **文档知识库**——客户上传的规章制度、历史材料、标准条款、产品与工艺资料，支持检索引用并在产出中标注来源；
  2. **模板与口径资产**——本机构的公文格式、报表模板、字段定义与计算口径（如某指标本单位是怎么统计的）；
  3. **修改意见回写**——用户对 AI 产出的修改与审核意见结构化留存，下次同类任务自动作为约束应用。
- **业务规则**：
  - 资产分级：平台通用 / 租户共享 / 工作区专属 / 个人私有，按优先级合并生效；
  - 知识库权限必须读写分离（可查看不等于可编辑或删除）；
  - 检索必须强制携带租户与权限过滤，不允许跨租户召回；
  - 资产更新有版本记录与操作审计，可回溯「是谁、什么时候改的」。
- **输入/输出**：输入为文档上传、模板定义、用户修改行为；输出为被引用的知识片段与被应用的约束。

### 3.5 交付物产出

- **功能描述**：产出原生可编辑的 Office 文件（docx / xlsx / pptx）以及 Markdown、PDF、HTML 等格式，支持基于机构模板套版。
- **业务规则**：
  - 生成后必须做打开校验，确认在 Microsoft Office 与 WPS 中版式正确，校验不通过则自动重试或降级；
  - 产出文件保留与源数据、执行任务的关联关系，可追溯每个数据项的来源；
  - 表格类产出必须保留公式与数据格式，不允许退化为纯文本；
  - 支持在平台内预览，并可下载或推送到客户自有存储。
- **输入/输出**：输入为执行结果数据 + 模板；输出为可编辑文件。

### 3.6 技能（Skill）扩展体系

- **功能描述**：以 Skill 形式封装可复用的工作方法与领域规范，运行时按需加载注入上下文。
- **业务规则**：
  - 三级命名空间：平台共享 / 租户私有 / 会话临时，按优先级合并，会话临时技能有生存期限制并自动回收；
  - 支持通过管理后台上传、启停、按租户绑定，变更即时生效无需发版；
  - 技能内容有版本管理与变更审计；
  - 多节点部署时保证各节点技能视图一致。
- **输入/输出**：输入为技能包上传与绑定配置；输出为运行时生效的能力集合。

### 3.7 工具与数据接入

- **功能描述**：提供文件读写、表格解析与计算、联网搜索、代码执行（数据处理与图表生成）、定时任务等基础工具；支持接入客户自有数据源。
- **业务规则**：
  - 工具调用统一经网关转发，由网关做身份识别、租户路由、权限校验与审计，不在 Agent 侧判断权限；
  - 代码执行在隔离沙箱内进行，默认全断网，仅放通显式白名单域名，出网流量强制经审计；
  - 定时任务支持周期与一次性两类，到点自动执行并投递结果。
- **输入/输出**：输入为工具调用请求；输出为工具执行结果与审计记录。

### 3.8 账号、租户与权限

- **功能描述**：租户 / 工作区 / 用户三层组织模型。租户对应一所学校或一家企业，工作区对应部门或项目组，用户归属工作区并持有角色。
- **业务规则**：
  - 所有业务数据无条件携带租户标识，并施加行级隔离；私有化部署时租户数为 1，但组织模型不简化；
  - 角色至少包含：平台管理员、租户管理员、工作区管理员、普通成员；
  - 会话、任务、知识资产默认归属创建者与其工作区，可显式共享；
  - 支持统一身份认证对接（SaaS 形态），企业级目录同步作为高档位能力。
- **输入/输出**：输入为身份凭证与组织配置；输出为带租户上下文的会话。

### 3.9 用量计量与配额

- **功能描述**：统一的计量事件流，对模型消耗、沙箱执行时长、检索请求等全量埋点。
- **业务规则**：
  - **计量埋点在两种形态下完全一致，结算层分叉**——SaaS 形态扣减额度并在耗尽时熔断；私有化形态只上报不扣费，配额转为并发与速率硬限制；
  - 额度消耗以**产物与任务**为计量单位对用户呈现，不以会话次数呈现；
  - 必须支持单用户级熔断——防止极少数重度用户击穿整体成本；
  - 租户管理员可见用量分布与产出看板。
- **输入/输出**：输入为各环节计量事件；输出为用量报表与配额状态。

### 3.10 模型接入与路由

- **功能描述**：模型可插拔，支持多提供方与本地部署模型；按任务节点分层路由。
- **业务规则**：
  - 默认使用轻量档模型执行，旗舰档仅用于任务规划与结果裁决节点；
  - 必须支持上下文缓存以降低成本；
  - **模型可热替换且不需要重新部署**——这是私有化形态的硬要求；
  - 路由策略变更必须通过回归评测门禁（覆盖两个行业核心场景的用例集）才允许生效。
- **输入/输出**：输入为模型配置与路由策略；输出为模型调用结果。

### 3.11 部署与交付

- **功能描述**：容器化交付，支持部署到客户云环境或本地服务器；提供 SaaS 多租户托管形态。
- **业务规则**：
  - 私有化部署以单机 Compose 形态为默认交付方式，**不要求客户具备容器编排运维能力**；
  - 提供安装前环境自检与安装后自检，输出可读的诊断结论；
  - 提供国产化环境适配（国产 CPU / 操作系统 / 数据库）作为进入相关采购清单的前置条件；
  - 提供可回答「为什么出错、怎么排查」的自助排障知识库，而非仅罗列操作步骤。
- **输入/输出**：输入为部署配置；输出为可运行实例与自检报告。

## 4. 页面与交互

### 4.1 主用户旅程

**核心链路**：选场景卡 → 投喂材料与要点 → 提交后异步执行（期间可另起会话问别的）→ 取回可编辑交付物 → 修改意见与口径回写沉淀 → 下次同类任务自动复用。

**页面间关系**：场景工作台为首页枢纽；向下进入会话执行页（承载对话与任务进度）；任务中心横向汇总所有任务；知识资产与管理后台为侧边独立入口。

**全局交互规则**：
- 登录后进入所属工作区上下文，切换工作区时会话与资产范围随之切换；
- 任务执行是全局态——用户在任意页面都能看到进行中任务的数量与状态，完成时主动提示；
- 高危动作统一以确认卡片拦截，不静默执行；
- 移动端 Web 提供完整的查看、追问、取回产物能力，创建复杂任务与管理后台以桌面端为主。

### 4.2 场景工作台（首页）

- **页面用途**：让用户无需构思 prompt 即可发起高质量任务。
- **核心元素**：场景卡分组网格（按行业与职能）、搜索场景、最近任务与最近产出、进行中任务提示条、自由对话入口。
- **用户操作流程**：浏览或搜索场景 → 点击卡片 → 引导式填写要点与上传材料 → 提交执行。
- **状态与反馈**：首次进入的空态引导（推荐 3 个最快见效的场景）、无匹配场景时引导使用自由对话、进行中任务的常驻提示。

### 4.3 会话执行页

- **页面用途**：承载任务执行过程的可见化与用户追问。
- **核心元素**：对话消息流、任务执行进度卡（步骤列表 + 当前动作 + 已产出中间物）、产出物卡片（预览 / 下载 / 继续修改）、引用来源标注、输入区（支持附件与知识库引用）。
- **用户操作流程**：查看执行进度 → 对中间结果提出调整 → 或在任务执行期间直接提出新问题（不打断原任务）→ 任务完成后预览并取回产物 → 提出修改意见（触发回写沉淀）。
- **状态与反馈**：任务排队中 / 执行中（步骤级进度）/ 等待用户确认（高危动作或信息缺口）/ 已完成 / 失败（保留中间物与失败原因，可重试）。

### 4.4 任务中心

- **页面用途**：统一管理所有异步任务，解决「任务与会话分离」后的可管理性。
- **核心元素**：任务列表（状态筛选、场景筛选、时间排序）、任务详情（执行日志、产物、消耗）、批量操作（取消 / 重试）、并发占用提示。
- **用户操作流程**：查看任务状态 → 进入详情查看日志与产物 → 取消或重试 → 跳回来源会话。
- **状态与反馈**：无任务空态、并发已达上限提示（含升档引导）、失败任务的原因归类展示。

### 4.5 知识资产页

- **页面用途**：管理机构的文档知识库、模板与口径资产。
- **核心元素**：知识库列表与文档上传、文档解析状态、模板库、字段口径定义表、资产生效范围设置（平台/租户/工作区/个人）、版本与变更记录。
- **用户操作流程**：创建知识库 → 上传文档并等待解析 → 设置可见范围与读写权限 → 在任务中被引用。
- **状态与反馈**：解析中 / 解析失败（含原因与可重试）/ 已就绪；权限不足时的明确提示（区分不可见与不可编辑）。

### 4.6 管理后台

- **页面用途**：租户管理员的组织、权限、技能、用量与模型配置入口。
- **核心元素**：成员与角色管理、工作区管理、技能包管理（上传 / 启停 / 绑定）、场景卡管理、用量与产出看板、模型与路由配置、审计日志。
- **用户操作流程**：配置组织与权限 → 上传并启用技能与场景 → 查看用量与采纳情况 → 调整模型与配额。
- **状态与反馈**：配置变更即时生效提示、用量接近配额预警、审计日志可检索。

> **管理者可见的使用与产出看板是采纳机制的一部分，不是附属报表**——调研显示「上级明确要求使用」是提升员工 AI 熟练度的最强杠杆。

### 4.7 移动端 Web

- **页面用途**：移动场景下的查看、追问与取回。
- **核心元素**：任务状态列表、会话追问、产物预览与分享、任务完成通知。
- **用户操作流程**：收到任务完成提示 → 查看产物 → 追问或要求调整 → 分享或转发。
- **状态与反馈**：适配小屏的进度展示；不支持的复杂操作明确引导至桌面端。

## 5. 非目标

- ~~设备数据采集与 MES / ERP 深度集成~~ — 需打设备与协议的重资产战场，已有专门的轻量 SaaS 占据；与「文档密集型办公」的能力甜区不重叠。
- ~~开放式技能市场与低代码编排画布~~ — 目标用户不具备自建应用能力，做了也无人使用；与既有 Agent 开发平台正面竞争无胜算。
- ~~视觉质检 / 设备预测性维护~~ — 工业大模型的主战场已有大量厂商投入，与本产品定位无关。
- ~~移动端原生 App~~ — 首期只做移动端 Web，架构层面预留接口；原生 App 待场景验证后再投入。
- ~~自研模型与模型训练能力~~ — 模型保持可替换即可；训练属于算力底座厂商的业务范畴（对应千万级算力预算科目），不是 Agent 平台的预算科目。
- ~~按人按月的席位订阅作为主要商业模型~~ — 中国市场数据不支持（办公软件付费率不足 15%、获客成本与小客户年费倒挂、回本期超两年），且目标客户预算科目属于采购资产而非费用。
- ~~Agent 直接操作用户本机文件系统（整理桌面、操作本地邮件客户端）~~ — 需在用户本机安装客户端，且与沙箱隔离存在结构性冲突；风险最高而不在首期两个重点场景内。一期改为「受控挂载」模式：用户显式授权目录后，Agent 在沙箱内访问该目录。详见[安全策略决策 1](./security-policy.md)。
- ~~Agent 拼装并执行任意 shell 命令~~ — 内核层对 bash 零防护（无命令黑名单、无默认超时、无路径约束），开放自由 shell 会带来长期的绕过对抗成本。一期改为「结构化工具」模式：文件操作、格式转换、数据分析等能力各自封装为参数经校验的工具，`bash` 工具默认不激活。详见[安全策略决策 4](./security-policy.md)。

## 6. 验收标准

### 场景工作台与交互入口

- [ ] 首页展示按行业与职能分组的场景卡，两个首期重点行业各有不少于 5 个可用场景
- [ ] 任一场景卡可在不输入自由文本 prompt 的前提下完成任务提交
- [ ] 必需输入未齐备时阻止提交并明确提示缺什么
- [ ] 租户自建场景可覆盖同名平台预置场景

### Agent 执行与异步任务

- [ ] 任务提交后用户可在同一会话继续提问，原任务不中断、不受影响
- [ ] 任务执行进度以步骤级粒度实时展示，含当前动作与已产出中间物
- [ ] 执行节点强制重启后，任务可从检查点续跑，已完成步骤不重复消耗模型调用
- [ ] 任务支持取消与重试；失败任务保留中间产物与可读的失败原因
- [ ] 主 Agent 可派发并行子 Agent，子 Agent 间上下文隔离且结果能正确汇总（需自建扩展实现）
- [ ] 高危动作（对外发送、批量修改、删除）必须经用户确认才执行
- [ ] 并发任务数按档位限制生效，达上限时给出明确提示与升档引导

### 机构知识资产

- [ ] 上传文档后可被任务检索引用，且产出中标注来源
- [ ] 知识库权限实现读写分离——可查看不等于可编辑或删除
- [ ] 跨租户检索隔离有效：任何情况下不召回其他租户的内容
- [ ] 用户对产出的修改意见被结构化留存，下次同类任务自动作为约束应用（可通过对比两次产出验证）
- [ ] 模板与字段口径资产按平台/租户/工作区/个人四级优先级正确合并生效
- [ ] 资产变更留有版本与操作审计，可回溯修改人与时间

### 交付物产出

- [ ] 产出的 docx / xlsx / pptx 在 Microsoft Office 与 WPS 中打开版式正确，抽样保真率 ≥ 95%
- [ ] 表格类产出保留公式与数据格式，未退化为纯文本
- [ ] 生成后自动打开校验，校验失败时自动重试或降级并告知用户
- [ ] 产出文件可追溯到源数据与执行任务

### 技能体系

- [ ] 技能三级命名空间（平台共享 / 租户私有 / 会话临时）按优先级正确合并注入
- [ ] 通过管理后台上传技能后即时生效，无需重新发版或重启
- [ ] 会话级临时技能在生存期结束后自动回收
- [ ] 多节点部署下各节点技能视图一致
- [ ] 技能的上传、启停、绑定操作全部写入审计

### 租户、权限与计量

- [ ] 所有业务数据表携带租户标识并施加行级隔离
- [ ] 私有化部署（租户数为 1）与 SaaS 部署使用同一套数据模型与组织模型，无 schema 分叉
- [ ] 四类角色的权限边界符合定义，越权操作被拒绝并记录
- [ ] 计量事件在两种形态下埋点一致；SaaS 形态额度耗尽时正确熔断，私有化形态转为并发与速率限制
- [ ] 单用户级熔断生效，可防止个别重度用户击穿整体成本
- [ ] 额度消耗以产物与任务为单位向用户呈现

### 模型与成本

- [ ] 模型可热替换且无需重新部署即可生效
- [ ] 分层路由生效：常规执行走轻量档，规划与裁决走旗舰档
- [ ] 上下文缓存生效，可观测到缓存命中率与成本下降
- [ ] 路由策略变更须通过覆盖两个行业核心场景的回归评测门禁才允许上线
- [ ] 100 人规模机构的常规使用下，单租户模型成本 ≤ 10 元/人/月

### 部署与交付

- [ ] 客户自有 IT 人员（不具备容器编排能力）可在 2 小时内独立完成私有化安装
- [ ] 提供安装前环境自检与安装后功能自检，输出可读诊断结论
- [ ] 沙箱默认全断网，仅放通显式白名单域名，出网流量经审计
- [ ] 完成国产化环境（国产 CPU / 操作系统 / 数据库）适配验证
- [ ] 自助排障知识库可回答「为什么出错、如何排查」类问题，而非仅操作步骤

### 采纳效果（上线后验证）

- [ ] 新开通账号首周产出至少一份可交付物的占比 ≥ 60%
- [ ] 席位周活率 ≥ 40%
- [ ] 管理者可在后台看到成员使用与产出分布
- [ ] 客户侧实测单份材料人工耗时降幅 ≥ 50%

## 7. 能力分层与自建边界

Pi 内核的极简哲学决定了本产品的工程量分布。明确这条边界，是排期估算与技术选型的前提。

### Pi 内核提供（通过 SDK 或 RPC 嵌入，不改内核源码）

| 能力 | 对本产品的作用 |
|---|---|
| Agent Loop 与四个基础工具原语 | 任务执行的最内核 |
| 多提供方模型统一接入（15+ 提供方，含本地模型） | 直接满足「模型可热替换」的硬要求 |
| 会话中途切换模型、跨提供方上下文交接 | 支撑分层路由（轻量档执行 / 旗舰档规划） |
| 树状可分叉会话历史（append-only，可回到任意历史点分叉） | 支撑「同一材料试多个版本」的办公场景 |
| 技能按需加载（渐进式披露，不破坏提示缓存） | 支撑行业技能包体系且不牺牲缓存命中率 |
| 上下文自动压缩（可定制摘要策略） | 长任务的上下文管理 |
| 中途插话与排队追问（steering） | **「任务执行中可继续对话」的会话内底层原语** |
| 扩展系统（20+ 生命周期钩子、运行时编译、热加载） | 所有自建能力的接入点 |

### 本产品自建（工程量主体）

| 层 | 说明 | 为何必须自建 |
|---|---|---|
| 子 Agent 并行 | 主 Agent 拆解、并行派发、上下文隔离、结果汇总 | Pi 刻意不内置，官方路径是扩展或多实例 |
| 异步任务编排 | 任务标识、状态持久化、检查点续跑、任务中心 | Pi 只有会话级 steering，无任务级编排 |
| 权限与沙箱 | 默认拒绝 + 白名单、高危动作人工确认、执行隔离 | Pi 刻意不做权限弹窗，官方建议容器隔离 |
| 多租户与组织模型 | 租户/工作区/用户三层、行级隔离、角色权限 | Pi 是单机 CLI 形态，无租户概念 |
| 机构知识资产 | 文档知识库、模板与口径、修改意见回写 | 需借助扩展钩子自行实现检索与长期记忆 |
| 场景工作台 | 场景卡、引导式要点收集、prompt 封装 | 产品层能力，与 Pi 无关 |
| Office 交付物产出 | 原生 docx/xlsx/pptx 生成与格式保真校验 | 需作为自定义工具接入 |
| 计量与配额 | 统一计量事件流、双形态结算分叉、单用户熔断 | 商业化能力，需自建 |
| 管理后台与多端前端 | 桌面 Web、移动 Web、租户管理后台 | Pi 仅提供终端 UI 与 Web 组件库作为起点 |
| 私有化交付 | 单机容器化部署包、环境自检、国产化适配 | 交付工程，需自建 |

> **一句话**：Pi 给的是可靠的发动机与变速箱，整车（车身、座舱、仪表、安全系统、生产线）都要自己造。这恰好与产品定位吻合——差异化本就不该建立在内核上。

## 8. 分期建议

| 阶段 | 范围 | 目标 |
|------|------|------|
| **一期（SaaS 先行）** | 场景工作台、Agent 执行引擎、异步任务与并行会话、知识库与模板口径资产、Office 产出、租户三层模型、计量埋点、桌面 Web + 移动 Web | 在 SaaS 形态上把两个行业各一个重点场景跑通打磨；架构按双形态设计（全表租户标识、Runner 抽象、统一计量事件流） |
| **二期（私有化交付）** | 单机 Compose 交付包、环境自检与安装自检、容器沙箱实现、国产化适配、自助排障知识库、私有化结算层（并发速率限制） | 形成可交付的私有化产品，支撑首单落地 |
| **三期（深化与扩展）** | 修改意见回写的自动化程度提升、技能与场景的租户自建能力、定时任务与主动服务、管理者采纳看板深化 | 强化护城河，提升续约与扩容 |

> 架构层面的三项必须在一期完成，后补代价是重写级别：**全表携带租户标识、沙箱 Runner 抽象、统一计量事件流**。

## 9. 待确认事项

1. **Pi 内核的授权与版本策略** — Pi 为 MIT 协议，允许商业闭源使用与再分发（保留版权声明即可）。但需注意两点：其一，Pi 已于 2026 年 4 月被 Earendil 收购，该公司同时推出了商业云平台 Lefos，需确认所采用版本的协议状态未发生变更；其二，需明确是跟随上游版本升级（获得持续改进但需适配变更），还是锁定版本自行维护分支（可控但失去上游红利）。建议跟随上游，且所有扩展只走官方扩展点、不改内核源码。
2. **与阿里系桌面办公 Agent 的竞争应对** — 直接对手已上线且功能三件套齐备，其企业版是否支持私有化目前未公开。建议单独立项跟踪。
3. **首批目标客户与试点单位** — 两个重点场景的打磨需要真实客户参与，需确认是否已有可落地的试点单位。
