# Agent 安全策略草案

> **状态：草案，待产品与安全负责人评审拍板。** 本文件标注 🔷 的条目需要你决策，其余为基于实测的硬结论。
>
> 本策略阻塞 M1 开发——权限模型不定，Agent 执行链路无法动工。

---

## 0. 为什么这份文档必须存在

用户场景包含「**让 Agent 帮忙执行 CLI 命令，如整理邮件、整理桌面**」。这是本产品能力最强、也**风险最高**的部分：它要求 Agent 操作用户的真实文件系统。

### 实测结论：内核层零防护

以下全部经 vendor 源码核实（非文档推断）：

| 检查项 | 实测结果 | 源码位置 |
|---|---|---|
| bash 工具命令黑名单 | **不存在** | `tools/bash.ts` 全文无 blocklist/denylist/校验逻辑 |
| bash 默认超时 | **无**。`timeout === undefined` 直接返回 undefined，即无限运行 | `tools/bash.ts:25-29` |
| 文件工具路径约束 | **无**。参数描述明文写 "relative or absolute"，接受任意绝对路径 | `tools/write.ts:12`、`read.ts:15` |
| 路径越界检查 | **不存在**。`path-utils.ts` 全部是 macOS 文件名编码兼容逻辑，无边界判断 | `tools/path-utils.ts` |
| 内置权限系统 | **不存在**。上游 README 原话：不含用于限制文件系统、进程、网络或凭据访问的内置权限系统，默认以启动它的用户与进程的权限运行 | 上游 README |

**结论**：模型可以直接写 `/etc/passwd`、可以 `rm -rf`、可以跑一条永不结束的命令。**全部防护必须由本产品提供。**

### 风险的商业含量

目标客户是高校与制造业。一次误删客户的评估材料、或删掉工艺图纸，造成的**商誉损伤远超技术修复成本**，且这类客户之间口碑传播极快。安全事故在这个市场是生存问题，不是体验问题。

## 1. 核心矛盾：沙箱 vs 真实文件

**必须正视一个结构性冲突：**

- 沙箱的意义是**隔离文件系统**
- 而"整理桌面/邮件"的场景恰恰要求**访问真实文件系统**

这两件事无法同时最大化。因此本策略的核心不是"要不要沙箱"，而是**把不同风险等级的场景分配到不同的执行环境**。

### 三类执行环境

| 环境 | 文件系统视图 | 适用场景 | 风险 |
|---|---|---|---|
| **A. 全隔离沙箱** | 仅任务工作区（临时卷），无用户真实文件 | 生成文档、数据计算、格式转换、检索问答 | 低 |
| **B. 受控挂载沙箱** | 沙箱内，但挂载用户**显式授权的目录**（只读或读写按配置） | 整理指定文件夹、批量重命名、多表核对 | 中 |
| **C. 用户终端代理** | 用户本机真实文件系统 | 整理桌面、操作本地邮件客户端 | **高** |

**🔷 决策点 1：C 类环境是否纳入一期？**

我的建议：**一期只做 A 与 B，C 类推迟。**

理由：
- A 类覆盖 Spec 首期两个重点场景（评估材料生成、体系文件与质量报告）的绝大部分
- B 类覆盖"多表核对"这类需要读用户文件的场景，且风险可控
- C 类（动用户桌面）风险最高、技术复杂度最高（需要在用户本机装客户端）、且**不在 Spec 首期重点场景内**
- 先用 A/B 建立产品信誉，再开放 C 类，商业上更稳

若你坚持一期要 C 类，则本文档第 5 节的约束必须全部实现，不可裁剪。

## 2. 文件系统访问分级

### 2.1 四级路径策略

任何文件操作在执行前必须归入以下四级之一：

| 级别 | 含义 | 默认范围 | 越权处理 |
|---|---|---|---|
| **W · 可读写** | Agent 可自由读写创建删除 | 任务工作区 `/workspace/<task_id>/` | — |
| **R · 只读** | 可读，禁止任何写操作 | 用户显式授权的输入目录、知识库物化目录、技能目录 | 拦截并告知 |
| **C · 需确认** | 每次操作弹确认卡片，用户逐次批准 | 用户授权的读写目录中的**删除**与**覆盖**操作 | 转 AWAIT_CONFIRM |
| **D · 完全禁止** | 不可见、不可访问 | 见下方黑名单 | 拦截 + 记审计 + 告警 |

### 2.2 D 级黑名单（不可配置，硬编码）

即使租户管理员也不得放开：

```
系统关键路径
  /etc  /sys  /proc  /boot  /dev  /root
  C:\Windows  C:\Program Files  注册表

凭据与密钥
  ~/.ssh  ~/.aws  ~/.kube  ~/.docker/config.json
  ~/.gnupg  *.pem  *.key  *.p12  id_rsa*
  任何 .env 文件

本产品自身
  vendor/           内核源码，防止 Agent 自我修改
  产品安装目录      防止提权
  会话与审计存储    防止篡改证据

其他租户的一切
  按 tenant_id 物理隔离，不同租户路径不可见
```

**🔷 决策点 2：`~/.ssh` 等凭据路径是否绝对禁止，还是允许租户显式放开？**

我的建议：**绝对禁止，不留配置口子。** 一旦允许配置，就会有客户为了图方便放开，而这类事故一旦发生是灾难级。宁可牺牲少数场景。

### 2.3 授权目录的获取方式

**用户必须显式授权，不做隐式推断。**

- 授权以「目录 + 权限级别（R/W）+ 有效期」为单位
- 授权在**场景卡定义**或**任务提交时**声明，不允许 Agent 运行中自行申请扩权
- 每次授权写入审计
- 🔷 **决策点 3**：授权是一次性（单任务）还是可持久（租户级长期授权）？建议**默认单任务，长期授权需租户管理员批准**

## 3. 命令执行策略

### 3.1 三档命令分类

| 档位 | 处理 | 示例 |
|---|---|---|
| **允许** | 直接执行 | 读类与计算类：`ls` `cat` `grep` `find` `wc` `head` `tail` `sort` `diff` `python`（沙箱内） |
| **需确认** | 弹确认卡片，展示完整命令原文，用户批准后执行 | 写类与移动类：`mv` `cp` `rm`（单文件）`chmod` `mkdir` `unzip`、批量重命名 |
| **禁止** | 直接拦截，记审计 | 见下 |

### 3.2 禁止命令（硬编码，不可配置）

```
破坏性批量操作
  rm -rf /   rm -rf ~   rm -rf *（无明确路径的递归删除）
  mkfs  dd  fdisk  shred
  find ... -delete（无路径限定）

提权与账户
  sudo  su  passwd  useradd  usermod  visudo

网络外传
  curl/wget 向非白名单域名 POST/PUT
  scp  rsync 到外部主机
  nc  ncat  socat
  git push（防止代码或数据外流）

进程与服务
  kill -9（对非自身进程）  systemctl  service  reboot  shutdown

包安装（防供应链注入）
  npm install  pip install  apt  yum  brew
  （沙箱镜像预装所需依赖，运行时不允许装包）

规避检测
  base64 解码后执行  eval  管道到 sh/bash
  history 清除
```

### 3.3 命令拦截的实现位置

用 `tool_call` 扩展钩子（审计 §6 确认可行），有两条 fail-safe 特性对我们有利：

- **handler 抛异常即阻断工具**（上游文档明示）
- 官方 `permission-gate.ts` 示例在 `!ctx.hasUI` 时默认阻断 —— 正是无头服务的正确行为

**默认拒绝**：白名单未命中即拒绝，而非黑名单未命中即放行。

> ⚠️ **实现警告**（审计 §3）：`event.input` 原地修改后 **Pi 不再重新校验**。因此若在钩子里改写命令参数，改写逻辑自身必须做完整校验，不能依赖内核兜底。

### 3.4 命令解析的对抗性考虑

**不能简单做字符串匹配**，攻击面包括：

| 绕过手法 | 防御 |
|---|---|
| `r''m -rf /`、`r\m` | 先做 shell 词法解析，取规范化后的可执行名 |
| `$(echo cm0=\|base64 -d)` | 禁止命令替换与 base64 管道执行 |
| `;` `&&` `\|\|` `\|` 串联多条命令 | 拆成单条逐一判定，任一条被禁则整体拒绝 |
| 别名与软链接指向危险命令 | 沙箱镜像固化 PATH，禁用用户级别名 |
| 通过 `python -c "os.system(...)"` 逃逸 | 解释器视为需确认档；沙箱内限制其能力 |

**🔷 决策点 4：命令解析要做到多严？**

选项 A（推荐）：**只允许白名单内的固定命令模板**，不接受自由拼装的 shell。Agent 要执行操作时调用结构化工具（如 `move_file(from, to)`）而非拼 shell 字符串。
- 优点：攻击面收窄到几乎为零，可审计性最好
- 缺点：灵活性降低，"整理邮件"这类场景要预先定义好工具

选项 B：允许自由 shell，但做严格词法解析 + 白名单。
- 优点：灵活
- 缺点：对抗成本高，长期会不断出现绕过手法

我的建议是 **A**。理由：目标用户不需要"任意 shell"的灵活性，他们需要的是"整理文件夹"这类**有限且明确**的能力。把这些能力做成结构化工具，既安全又更可控（还能给出更好的进度展示）。

## 4. 沙箱与网络

### 4.1 沙箱实现（双形态必须分叉）

| 形态 | 实现 | 原因 |
|---|---|---|
| SaaS | microVM 级隔离 | 多租户高密度下威胁模型正确 |
| 私有化 | 容器 + seccomp 白名单 | **客户常拿不到 `/dev/kvm`**（自身跑在虚机内、嵌套虚拟化未开），microVM 方案装不上 |

共用 `SandboxProvider` 抽象：`create / exec / pause / resume / kill` + 网络策略 + 资源上限。

### 4.2 网络铁律（两形态一致，不可配置放开）

> **默认全断网，仅放通显式域名白名单，出网流量强制经审计代理。**

最常见的生产事故是**隔离完美的沙箱配了无限制出网** —— 隔离了文件系统却留了数据外传通道，等于没隔离。

白名单默认只含：
- 配置的模型 API 端点
- 本产品自身的服务端点

**🔷 决策点 5：是否允许 Agent 联网搜索？** Spec 3.7 提到「联网搜索」工具。
建议：**通过本产品的搜索代理服务出网，而非让沙箱直连互联网。** 这样搜索能力保留，但沙箱仍全断网，且搜索内容可审计。

### 4.3 资源上限（防失控与拒绝服务）

| 限制 | 默认值 | 依据 |
|---|---|---|
| 单条命令超时 | **120 秒** | 内核无默认超时（实测 `bash.ts:25-29`），必须外部强制 |
| 单任务墙钟 | 30 分钟 | 防失控循环 |
| 单任务工具调用步数 | 200 步 | 同上 |
| Runner 内存 | 2 GB | 防 OOM 拖垮宿主 |
| Runner CPU | 按档位配额 | 防单租户占满 |
| 单任务磁盘写入 | 1 GB | 防写满磁盘 |
| 沙箱进程数 | 64 | 防 fork bomb |

> ⚠️ 超时必须由**宿主强制**（外部墙钟 + 强杀），不能依赖模型传 `timeout` 参数 —— 那是可选参数，模型可能不传。

## 5. 若开放 C 类（用户终端代理），额外的硬约束

**仅当决策点 1 选择一期包含 C 类时适用。以下每条都不可裁剪。**

1. **必须有本机客户端**，且客户端自身实现路径白名单，不信任服务端下发的路径
2. **首次授权必须有明确的目录选择界面**，用户手动勾选可访问目录，不接受通配符或家目录整体授权
3. **所有写操作必须先备份**：移动/覆盖/删除前先把原文件复制到回收区，保留 7 天可恢复
4. **删除操作永不真删**：一律移入回收区，由用户手动清空
5. **操作预览必选**：执行前展示完整的变更清单（哪些文件将被移动到哪里），用户确认后才执行
6. **单次操作文件数上限**（建议 100），超出需二次确认
7. **本机操作全量审计**并可在界面回溯
8. **提供一键撤销**：对最近一次批量操作可整体回滚

## 6. 审计要求

以下事件**必须**全量记录，且审计存储对 Agent 不可写（D 级黑名单已覆盖）：

| 事件 | 记录内容 |
|---|---|
| 工具调用 | 租户/用户/任务、工具名、完整参数、结果摘要、耗时 |
| 权限拦截 | 被拒的操作原文、命中的规则、时间 |
| 确认动作 | 谁在何时批准了什么操作 |
| 文件写操作 | 路径、操作类型、大小变化、备份位置 |
| 授权变更 | 谁给了哪个目录什么权限、有效期 |
| 出网请求 | 目标域名、是否命中白名单 |
| 资源超限 | 哪项超限、被强杀的任务 |

**保留期建议 180 天**（高校与制造业客户的审计与合规需求通常按年度检查）。

**🔷 决策点 7：审计日志是否需要防篡改（如追加写 + 哈希链）？** 建议：私有化形态提供，SaaS 形态默认开启。
