# Agent 安全策略

> **状态：全部决策点已拍板（见第 7 节汇总）。本策略已可作为 M1 的实现依据。**
>
> 每项决策在正文中标注 ✅ 并已转为可执行的设计约束。

---

## 0. 为什么这份文档必须存在

用户场景包含「**让 Agent 帮忙执行 CLI 命令，如整理邮件、整理桌面**」。这是本产品能力最强、也**风险最高**的部分：它要求 Agent 操作用户的真实文件系统。

### 实测结论：内核层零防护

以下全部经 vendor 源码核实（非文档推断）：

| 检查项 | 实测结果 | 源码位置 |
|---|---|---|
| bash 工具命令黑名单 | **不存在** | `tools/bash.ts` 全文无 blocklist/denylist/校验逻辑 |
| bash 默认超时 | **无**。`timeout === undefined` 直接返回 undefined，即无限运行 | `tools/bash.ts:25-29` |
| 文件工具路径约束 | **无**。参数描述明文写 "relative or absolute"，接受任意绝对路径 | `tools/write.ts:12`、`read.ts:15` |
| 路径越界检查 | **不存在**。`path-utils.ts` 全部是 macOS 文件名编码兼容逻辑，无边界判断 | `tools/path-utils.ts` |
| 内置权限系统 | **不存在**。上游 README 原话：不含用于限制文件系统、进程、网络或凭据访问的内置权限系统，默认以启动它的用户与进程的权限运行 | 上游 README |

**结论**：模型可以直接写 `/etc/passwd`、可以 `rm -rf`、可以跑一条永不结束的命令。**全部防护必须由本产品提供。**

### 风险的商业含量

目标客户是高校与制造业。一次误删客户的评估材料、或删掉工艺图纸，造成的**商誉损伤远超技术修复成本**，且这类客户之间口碑传播极快。安全事故在这个市场是生存问题，不是体验问题。

## 1. 核心矛盾：沙箱 vs 真实文件

**必须正视一个结构性冲突：**

- 沙箱的意义是**隔离文件系统**
- 而"整理桌面/邮件"的场景恰恰要求**访问真实文件系统**

这两件事无法同时最大化。因此本策略的核心不是"要不要沙箱"，而是**把不同风险等级的场景分配到不同的执行环境**。

### 三类执行环境

| 环境 | 文件系统视图 | 适用场景 | 风险 |
|---|---|---|---|
| **A. 全隔离沙箱** | 仅任务工作区（临时卷），无用户真实文件 | 生成文档、数据计算、格式转换、检索问答 | 低 |
| **B. 受控挂载沙箱** | 沙箱内，但挂载用户**显式授权的目录**（只读或读写按配置） | 整理指定文件夹、批量重命名、多表核对 | 中 |
| **C. 用户终端代理** | 用户本机真实文件系统 | 整理桌面、操作本地邮件客户端 | **高** |

**✅ 决策 1（已拍板）：C 类不纳入一期。**

一期只做 A（全隔离沙箱）与 B（受控挂载沙箱）。

据此产生的设计约束：
- 一期不开发本机客户端
- 本文第 5 节（终端代理的 8 条约束）**一期不适用**，保留供二期参考
- 决策点 6（回收区保留期与文件数上限）**随之作废**
- 「整理桌面/本地邮件客户端」场景移出一期范围，需回写 Spec 非目标章节

## 2. 文件系统访问分级

### 2.1 四级路径策略

任何文件操作在执行前必须归入以下四级之一：

| 级别 | 含义 | 默认范围 | 越权处理 |
|---|---|---|---|
| **W · 可读写** | Agent 可自由读写创建删除 | 任务工作区 `/workspace/<task_id>/` | — |
| **R · 只读** | 可读，禁止任何写操作 | 用户显式授权的输入目录、知识库物化目录、技能目录 | 拦截并告知 |
| **C · 需确认** | 每次操作弹确认卡片，用户逐次批准 | 用户授权的读写目录中的**删除**与**覆盖**操作 | 转 AWAIT_CONFIRM |
| **D · 完全禁止** | 不可见、不可访问 | 见下方黑名单 | 拦截 + 记审计 + 告警 |

### 2.2 D 级黑名单（不可配置，硬编码）

即使租户管理员也不得放开：

```
系统关键路径
  /etc  /sys  /proc  /boot  /dev  /root
  C:\Windows  C:\Program Files  注册表

凭据与密钥
  ~/.ssh  ~/.aws  ~/.kube  ~/.docker/config.json
  ~/.gnupg  *.pem  *.key  *.p12  id_rsa*
  任何 .env 文件

本产品自身
  vendor/           内核源码，防止 Agent 自我修改
  产品安装目录      防止提权
  会话与审计存储    防止篡改证据

其他租户的一切
  按 tenant_id 物理隔离，不同租户路径不可见
```

**✅ 决策 2（已拍板）：凭据路径绝对禁止，不留配置口子。**

上述 D 级黑名单**硬编码在代码中，不提供任何配置项放开**。即使租户管理员、即使客户书面要求，也不得开放。

据此产生的设计约束：
- 黑名单以常量形式写死，不从配置文件或数据库读取
- 不提供「高级设置」「专家模式」等任何绕过入口
- 命中黑名单时：拦截 + 写审计 + 触发告警（三者都要，不只是拦截）
- 理由：一旦留配置口子，就会有客户为图方便放开，而这类事故一旦发生是灾难级。宁可牺牲少数场景

### 2.3 授权目录的获取方式

**用户必须显式授权，不做隐式推断。**

- 授权以「目录 + 权限级别（R/W）+ 有效期」为单位
- 授权在**场景卡定义**或**任务提交时**声明，不允许 Agent 运行中自行申请扩权
- 每次授权写入审计
**✅ 决策 3（已拍板）：支持长期授权（租户级持久授权）。**

授权以「目录 + 权限级别（R/W）+ 有效期」为单位，支持两种模式：

| 模式 | 适用 | 批准方 | 有效期 |
|---|---|---|---|
| **单任务授权** | 临时性、一次性的文件访问 | 用户自己勾选 | 任务结束即失效 |
| **长期授权**（本次拍板支持） | 高频使用的共享目录（如部门共享盘、标准文件库） | **租户管理员** | 可设固定期限或长期有效 |

据此产生的设计约束：

1. **长期授权必须由租户管理员批准**，普通成员不能自行给自己开长期权限
2. 长期授权在管理后台有**独立的管理页面**，可列出全部生效中的长期授权（谁批的、批给谁、哪个目录、什么权限、何时批的、何时到期）
3. **必须支持随时撤销**，撤销立即生效（不等任务结束）
4. **必须有定期复核机制** —— 长期授权列表每季度提示管理员复核一次，避免「当年谁开的没人记得了」
5. 长期授权的每一次**实际使用**都要写审计（不只是授权时写一次）
6. 长期授权**不能覆盖 D 级黑名单** —— 黑名单优先级最高，不受任何授权影响
7. Agent 运行中**仍然不得自行申请扩权**，只能使用已有授权

> ⚠️ **风险提示**：长期授权的代价是权限长期敞开。若发生账号盗用或 Agent 误操作，影响面比单任务授权大。第 4 条的定期复核与第 3 条的即时撤销是主要缓解手段，实现时不可省略。

## 3. 命令执行策略

### 3.1 三档命令分类

| 档位 | 处理 | 示例 |
|---|---|---|
| **允许** | 直接执行 | 读类与计算类：`ls` `cat` `grep` `find` `wc` `head` `tail` `sort` `diff` `python`（沙箱内） |
| **需确认** | 弹确认卡片，展示完整命令原文，用户批准后执行 | 写类与移动类：`mv` `cp` `rm`（单文件）`chmod` `mkdir` `unzip`、批量重命名 |
| **禁止** | 直接拦截，记审计 | 见下 |

### 3.2 禁止命令（硬编码，不可配置）

```
破坏性批量操作
  rm -rf /   rm -rf ~   rm -rf *（无明确路径的递归删除）
  mkfs  dd  fdisk  shred
  find ... -delete（无路径限定）

提权与账户
  sudo  su  passwd  useradd  usermod  visudo

网络外传
  curl/wget 向非白名单域名 POST/PUT
  scp  rsync 到外部主机
  nc  ncat  socat
  git push（防止代码或数据外流）

进程与服务
  kill -9（对非自身进程）  systemctl  service  reboot  shutdown

包安装（防供应链注入）
  npm install  pip install  apt  yum  brew
  （沙箱镜像预装所需依赖，运行时不允许装包）

规避检测
  base64 解码后执行  eval  管道到 sh/bash
  history 清除
```

### 3.3 命令拦截的实现位置

用 `tool_call` 扩展钩子（审计 §6 确认可行），有两条 fail-safe 特性对我们有利：

- **handler 抛异常即阻断工具**（上游文档明示）
- 官方 `permission-gate.ts` 示例在 `!ctx.hasUI` 时默认阻断 —— 正是无头服务的正确行为

**默认拒绝**：白名单未命中即拒绝，而非黑名单未命中即放行。

> ⚠️ **实现警告**（审计 §3）：`event.input` 原地修改后 **Pi 不再重新校验**。因此若在钩子里改写命令参数，改写逻辑自身必须做完整校验，不能依赖内核兜底。

### 3.4 命令解析的对抗性考虑

**不能简单做字符串匹配**，攻击面包括：

| 绕过手法 | 防御 |
|---|---|
| `r''m -rf /`、`r\m` | 先做 shell 词法解析，取规范化后的可执行名 |
| `$(echo cm0=\|base64 -d)` | 禁止命令替换与 base64 管道执行 |
| `;` `&&` `\|\|` `\|` 串联多条命令 | 拆成单条逐一判定，任一条被禁则整体拒绝 |
| 别名与软链接指向危险命令 | 沙箱镜像固化 PATH，禁用用户级别名 |
| 通过 `python -c "os.system(...)"` 逃逸 | 解释器视为需确认档；沙箱内限制其能力 |

**✅ 决策 4（已拍板）：不开放自由 shell，只允许结构化工具。**

Agent **不能拼装任意 shell 命令字符串**。所有操作必须通过预定义的结构化工具完成，工具参数经 schema 校验。

据此产生的设计约束：

1. **`bash` 工具默认不激活**（Pi 默认激活 read/bash/edit/write 四个，需显式排除 bash）
2. 需要的能力逐个做成结构化工具，例如：
   - `list_dir(path)` / `read_file(path)` / `write_file(path, content)`
   - `move_file(from, to)` / `copy_file(from, to)` / `delete_file(path)`
   - `extract_archive(path, dest)` / `convert_format(path, target_format)`
   - `run_analysis(script_id, inputs)` —— 预置的数据分析脚本，不接受任意代码
3. 每个工具内部做路径校验（对照第 2 节四级策略），校验通过才执行
4. **本节 3.1–3.2 的命令分类与黑名单降级为「纵深防御的第二道闸」** —— 主防线是"根本没有 shell 可用"，黑名单用于兜住万一将来开放 bash 的情况
5. **本节 3.4 的对抗性解析问题基本消解** —— 没有自由 shell，就没有命令串联、命令替换、base64 绕过的攻击面

> ⚠️ **代价**：灵活性降低。用户想做的操作若无对应工具，Agent 无法完成。因此**工具集设计成为 M1 的关键工作**——需要从两个行业的真实场景反推需要哪些工具。
>
> ⚠️ **数据分析场景的特殊处理**：Spec 3.7 提到「代码执行（数据处理与图表生成）」。这与"不开放自由 shell"存在张力。一期处理方式：提供**受限的数据分析工具**（固定的 Excel 解析、统计计算、图表生成能力），而非让模型写任意 Python。若后续确需任意代码执行，必须在 A 类全隔离沙箱内、且全断网、且不挂载任何用户目录。

## 4. 沙箱与网络

### 4.1 沙箱实现（双形态必须分叉）

| 形态 | 实现 | 原因 |
|---|---|---|
| SaaS | microVM 级隔离 | 多租户高密度下威胁模型正确 |
| 私有化 | 容器 + seccomp 白名单 | **客户常拿不到 `/dev/kvm`**（自身跑在虚机内、嵌套虚拟化未开），microVM 方案装不上 |

共用 `SandboxProvider` 抽象：`create / exec / pause / resume / kill` + 网络策略 + 资源上限。

### 4.2 网络铁律（两形态一致，不可配置放开）

> **默认全断网，仅放通显式域名白名单，出网流量强制经审计代理。**

最常见的生产事故是**隔离完美的沙箱配了无限制出网** —— 隔离了文件系统却留了数据外传通道，等于没隔离。

白名单默认只含：
- 配置的模型 API 端点
- 本产品自身的服务端点

**✅ 决策 5（已拍板）：搜索经本产品的搜索代理服务出网，沙箱保持全断网。**

Agent 不直连互联网。联网搜索通过结构化工具 `web_search(query, options)` 发起，工具向平台的搜索代理服务请求，由代理去外网搜索并把结果递回沙箱内。

```
沙箱（全断网）                     平台侧                      外网
  Agent
   └ web_search(query) ──→ 搜索代理服务 ──→ 搜索引擎 / 内容抓取
                              │ 记审计
                              │ 结果清洗与截断
     结果 ←───────────────────┘
```

据此产生的设计约束：

1. **沙箱网络策略不变**：仍为默认全断网 + 域名白名单，白名单只含模型 API 与平台自身端点。**搜索不构成放开沙箱出网的理由。**
2. 搜索代理服务是**平台侧组件**，不在沙箱内
3. 代理层必须实现：
   - **出网审计** —— 记录每次搜索的租户/用户/任务、查询词、命中的结果源
   - **结果清洗** —— 剥离脚本与追踪像素，仅回传文本与必要元数据
   - **长度截断** —— 防止超长网页内容冲爆上下文窗口
   - **搜索源统一管控** —— 可按租户配置允许的搜索源；私有化形态可配置为仅检索客户内网资源或完全关闭
   - **结果缓存** —— 相同查询在有效期内复用，降低成本
4. **查询词本身要过敏感内容检查** —— 防止把客户机密内容（如工艺参数、图纸描述）作为查询词发到外网。命中时拦截并告知用户
5. 私有化形态下，搜索代理可被客户配置为**完全禁用**，产品功能应能优雅降级

> 💡 **为什么不给沙箱开网口**：一旦沙箱能直连外网，「数据不出门」在技术上即不成立——一次 prompt 注入或模型幻觉就可能把客户的工艺图纸内容编码进请求发出去，且无出网记录可查。而客户的安全审计必问「你的 AI 能不能上外网」。代理方案的实现成本很小（一个转发接口），但保住了核心商业叙事，并顺带获得审计、缓存、源管控三项能力。
>
> ⚠️ **内网访问与公网访问是两件事**：若后续需要 Agent 访问客户内网的其他业务系统，应单独放通内网白名单，**不等于**放开公网直连。

### 4.3 资源上限（防失控与拒绝服务）

| 限制 | 默认值 | 依据 |
|---|---|---|
| 单条命令超时 | **120 秒** | 内核无默认超时（实测 `bash.ts:25-29`），必须外部强制 |
| 单任务墙钟 | 30 分钟 | 防失控循环 |
| 单任务工具调用步数 | 200 步 | 同上 |
| Runner 内存 | 2 GB | 防 OOM 拖垮宿主 |
| Runner CPU | 按档位配额 | 防单租户占满 |
| 单任务磁盘写入 | 1 GB | 防写满磁盘 |
| 沙箱进程数 | 64 | 防 fork bomb |

> ⚠️ 超时必须由**宿主强制**（外部墙钟 + 强杀），不能依赖模型传 `timeout` 参数 —— 那是可选参数，模型可能不传。

## 5. 若开放 C 类（用户终端代理），额外的硬约束

> **⏸ 一期不适用。** 决策 1 已确定 C 类不纳入一期，本节保留供二期评估时参考。届时以下每条都不可裁剪。

1. **必须有本机客户端**，且客户端自身实现路径白名单，不信任服务端下发的路径
2. **首次授权必须有明确的目录选择界面**，用户手动勾选可访问目录，不接受通配符或家目录整体授权
3. **所有写操作必须先备份**：移动/覆盖/删除前先把原文件复制到回收区，保留 7 天可恢复
4. **删除操作永不真删**：一律移入回收区，由用户手动清空
5. **操作预览必选**：执行前展示完整的变更清单（哪些文件将被移动到哪里），用户确认后才执行
6. **单次操作文件数上限**（建议 100），超出需二次确认
7. **本机操作全量审计**并可在界面回溯
8. **提供一键撤销**：对最近一次批量操作可整体回滚

> 决策点 6（回收区保留期、单次操作文件数上限）已随决策 1 作废。

## 6. 审计要求

以下事件**必须**全量记录，且审计存储对 Agent 不可写（D 级黑名单已覆盖）：

| 事件 | 记录内容 |
|---|---|
| 工具调用 | 租户/用户/任务、工具名、完整参数、结果摘要、耗时 |
| 权限拦截 | 被拒的操作原文、命中的规则、时间 |
| 确认动作 | 谁在何时批准了什么操作 |
| 文件写操作 | 路径、操作类型、大小变化、备份位置 |
| 授权变更 | 谁给了哪个目录什么权限、有效期 |
| 出网请求 | 目标域名、是否命中白名单 |
| 资源超限 | 哪项超限、被强杀的任务 |

**保留期建议 180 天**（高校与制造业客户的审计与合规需求通常按年度检查）。

**✅ 决策 7（已拍板）：审计日志防篡改，两种形态均默认开启。**

审计日志采用**追加写 + 哈希链**保护完整性：每条记录携带自身内容的哈希，且该哈希包含上一条记录的哈希，形成链式结构。任何对历史记录的删改都会导致后续哈希校验失败，可被检测。

据此产生的设计约束：

1. **SaaS 与私有化两种形态均默认开启**，不提供关闭选项
2. 审计存储**仅支持追加**，不提供更新与删除接口（应用层无删除路径）
3. 提供**完整性校验工具**，可对指定时间段的审计链做全量校验并输出报告 —— 这既是自查手段，也是应对客户审计时的交付物
4. 审计存储路径在 D 级黑名单内（Agent 不可访问，已在 2.2 覆盖）
5. 保留期 180 天；到期归档而非直接删除，归档文件保留链尾哈希以维持可验证性
6. 校验失败时触发**高优先级告警**，并记录失败位置

> 💡 **商业价值**：目标客户含国企与高校，等保测评会检查审计日志的完整性保护。此项实现成本不高，但在投标与合规审查中是实质加分项。

## 7. 决策状态汇总

**七个决策点全部拍板，本策略可作为 M1 实现依据。**

| # | 决策点 | 结论 | 产生的主要约束 |
|---|---|---|---|
| 1 | 是否允许 Agent 操作用户真实桌面 | **不纳入一期** | 一期不做本机客户端；改为「受控挂载」模式；第 5 节一期不适用 |
| 2 | 凭据路径是否绝对禁止 | **绝对禁止，不留配置口子** | 黑名单硬编码为常量，无任何放开入口；命中即拦截+审计+告警 |
| 3 | 目录授权是单任务还是可持久 | **支持长期授权** | 长期授权须管理员批准；需独立管理页面、即时撤销、季度复核；不可覆盖黑名单 |
| 4 | 命令解析严格度 | **不开放自由 shell，只用结构化工具** | `bash` 默认不激活；工具集设计成为 M1 关键工作；对抗性解析问题基本消解 |
| 5 | 联网搜索的出网方式 | **经平台搜索代理，沙箱保持全断网** | 需实现搜索代理服务（出网审计、结果清洗、源管控、缓存、查询词敏感检查） |
| 7 | 审计防篡改 | **两种形态均默认开启** | 追加写 + 哈希链；提供完整性校验工具；仅追加无删除接口 |

**已作废**

| # | 决策点 | 原因 |
|---|---|---|
| 6 | C 类的回收期与文件数上限 | 决策 1 选择不纳入 C 类，本项无适用场景 |

### 决策 3 的风险提示（需在实现中落实缓解措施）

长期授权是本轮唯一**放宽**安全边界的决策。其代价是权限长期敞开，若发生账号盗用或 Agent 误操作，影响面大于单任务授权。**三项缓解措施不可省略**：

1. 即时撤销（不等任务结束）
2. 季度复核提示
3. 每次实际使用都写审计（不只授权时写一次）

### 对 M1 工作量的影响

本轮决策新增的实现项：

| 项 | 来源 | 工作量 |
|---|---|---|
| 结构化工具集（替代 bash） | 决策 4 | **大** —— 需从两行业真实场景反推工具清单 |
| 搜索代理服务 | 决策 5 | 小 —— 转发接口 + 审计 + 缓存 |
| 长期授权管理（后台页面、撤销、复核） | 决策 3 | 中 |
| 审计哈希链 + 校验工具 | 决策 7 | 小到中 |
| 硬编码黑名单 | 决策 2 | 小 |

决策 1 与 4 同时**减少**了工作量：不做本机客户端、不做命令词法解析与对抗防御。
