## 0. 三条决定全局的约束

在展开架构之前，先把最硬的三个发现摆在前面——它们不是实现细节，而是架构的地基。

> 🔄 **M0 验证后，约束 A 与 C 的事实判断被推翻，但架构决策全部保持不变**（理由从「被迫」变成「主动选择」）。修正过程完整保留，因为它记录了「审计针对的是 `coding-agent` 包、我们实际用的是 `agent` 包」这一关键区分 —— 这个区分影响后续每一次接口查阅。

### 约束 A（已修正）：隔离单元仍是进程，但不是被迫的

> 原判断为「Pi 有 4 个进程级全局单例，无法在单进程内承载多租户」。**[Spike 1](../spikes/README.md) 确认这 4 个单例全部位于 `coding-agent` 包**（`sdk.ts`、`core/http-dispatcher.ts`、`core/output-guard.ts`、`core/auth-storage.ts`），我们 vendor 的 `agent` 包里 `takeOverStdout` / `undici` / `setGlobalDispatcher` **零命中**。

实测（10/10 通过）：`agent` 包内消息历史 100% 挂在实例上，进程级可变状态只有一处 —— `src/stream-fn.ts:3` 的 `defaultStreamFn`，且只是个函数引用、不持有会话状态。底层 `Agent` 与 `Harness + Session` 两层，消息历史、模型侧 transcript、事件流三者均不串台。

**→ 架构决策不变：一会话一进程。** 但理由变了 —— 不是「内核不支持」，而是**沙箱隔离需求独立存在**（安全策略要求执行环境相互不可见）且进程级隔离额外提供故障域隔离。单进程多会话成为开发调试与轻量私有化部署的安全后备形态。

**→ 两条派生的硬约束**：多用户必须一人一 Session（同 Session 的多 lane 在 mutation line 上串行）；`RunnerAdapter` 必须显式传 `streamFn`（否则落到那处进程级全局）。

### 约束 B（成立）：Pi 无任何执行隔离

仓库 README 原话：Pi 不含用于限制文件系统、进程、网络或凭据访问的内置权限系统，默认以启动它的用户与进程的权限运行。`bash` 工具**无默认超时**。官方对隔离的唯一回答是容器化整个进程。

> ✅ **[Spike 3](../spikes/README.md) 的补充（7/7 通过）**：内核虽无权限系统，但提供了可用于自建权限门的钩子。`before_tool` 返回 `{ block: { reason } }` 能让工具的 `execute` **零次**被调用，且 **handler 抛异常时 fail-closed**（权限逻辑有 bug 时行为是拒绝而非放行）。被拒调用连执行意图都不落盘，崩溃恢复不会重放它。
>
> 另：内置工具全是工厂函数，**源码里没有任何自动注册** —— 不调 `createBashTool()` 就没有 bash，所以「无默认超时」这条在我们的配置下不生效（[安全策略决策 4](./security-policy.md) 的前提由此成立）。

**→ 沙箱是本产品必须自建的第一等工程，不是配置项。**

### 约束 C（已被 M0 推翻）：session 存储**是可替换的**

> 🔄 原判断为「不可替换，且零并发保护」，依据是 `coding-agent` 的 `SessionManager`（私有构造、硬依赖 `node:fs`、零加锁、`list()` 为 O(所有字节)）。**[Spike 2](../spikes/README.md) 确认那是另一套实现，我们不使用它。**

我们采用的 `agent/src/harness/session/` 是**为可替换而设计的两层接口**：

- `SessionRepo`（`types.ts:592`）与 `Storage`（`types.ts:455`）都是接口，`JsonlSessionRepo` / `MemorySessionRepo` 均为**公开构造函数**
- 生产代码**零 node builtin 依赖** —— 文件系统是注入的 `FileSystem` 能力
- 上游导出 conformance 测试套件（`./harness/session/testing`）专供第三方后端自检合规，自己也把 SQLite 后端拆成了独立包

并发保护方面：JSONL 后端确实零加锁，但**坏尾自愈已内建**（打开时若末行缺 `\n` 则丢弃并原子重写，上游有专门的 torn tail 测试），会话创建是**原子发布**（临时文件 + rename），写入是纯 append 且一事务一行。

**→ 直接实现自己的 `Storage` 后端即可，不改内核、无需「JSONL 落盘 + 事件镜像」双写。单写者由编排层的分布式租约保证；换数据库后端后由数据库事务承担。**

### 1.2 Pi 的嵌入方式：vendor 源码 + 子进程隔离

**决策分两层，不要混为一谈：**

**第一层 · 代码归属：vendor 进本仓库，不作为 npm 依赖。**

Pi 是 MIT 协议开源代码（非服务），授权永久且不可撤销。vendor 后本产品完整自包含：`git clone` 即可编译，上游任何状态变化（删库、下架、停止维护）均不影响。详见 [vendor/pi/README.md](../vendor/pi/README.md)。

| 维度 | npm 依赖 | **vendor（采纳）** |
|---|---|---|
| 上游删库 / 下架 | 无法重装 | ✅ 无影响 |
| 私有化构建需外网 | 需要 | ✅ 不需要 |
| 改内核 | 不可行 | ✅ 可改 |
| 客户代码审计 | 交不出 | ✅ 可交底 |
| 获取上游更新 | 改版本号即可 | ⚠️ 需手动评估合并 |

采纳理由：本产品是商业售卖的生产级系统，**自主可控的价值高于自动获取上游更新**。且私有化交付时客户机房常无外网，构建过程不能依赖 npm registry。

**vendor 范围**（约 6.7 万行，含测试）：

| 目录 | 改动政策 |
|---|---|
| `agent/`（Agent Loop、状态管理） | 可改 —— 子 Agent 与检查点需要 |
| `ai/`（多提供方接入） | **承诺不改** —— 保持升级为无痛覆盖，白拿新模型支持 |
| `coding-agent/core/tools/`（bash/read/write/edit） | 可改 —— 用户的 CLI 场景依赖此处 |
| `coding-agent/core/extensions/`（40 个钩子） | 可改 —— 权限门依赖此处 |

**刻意排除**：`tui`（终端字符界面，本产品前端是 Web）、`coding-agent` 的终端交互层。

**版本锁定**：`v0.87.1`（commit `f07218c4`，2026-09-22 正式发布点）。**不锁主干 HEAD** —— 审计期用的 `v0.87.1-17-g8676a0dc` 含 17 个未经发布验证的提交，生产系统不应采用中间状态。

**升级节奏**：每季度评估一次，不跟随主干。实测上游近 30 天 443 个提交、13 个月发 293 个版本（约每 1.4 天一个），跟随主干需长期专职人力。**变更时机由我们决定**是 to B 生产系统的核心能力。

> ⚠️ 上游是 0.x 版本，语义化版本规范允许 1.0 前在任意小版本破坏兼容性。**每次升级都须视为可能有 breaking change**，不可因"只是小版本"跳过回归测试。

**第二层 · 运行时隔离：每会话一个子进程，进程内直接调用 vendor 代码。**

| 方案 | 隔离 | 可编程注册工具 | 权限门 | 判定 |
|---|---|---|---|---|
| 进程内多 session | ❌ 4 个全局单例 | ✅ | ✅ | **排除**（约束 A） |
| 子进程跑现成 CLI（RPC 协议） | ✅ | ❌ RPC 不支持 | ⚠️ 仅磁盘扩展文件 | 仅作降级路径 |
| **子进程 + 进程内直调 vendor** | ✅ | ✅ | ✅ | **采纳** |

采纳理由：
1. 进程边界是 Pi 唯一真实提供的隔离边界，且可再嵌套容器/微虚机
2. RPC 面只有约 35 个操作且**无法编程注册自定义工具与权限门**，而这两项是 SaaS 硬需求；直接调用 vendor 代码可用完整的约 90 个成员 API
3. 崩溃收敛：OOM、失控 bash、异常扩展只杀一个租户的子进程
4. Pi 官方的 subagent 示例本身就是子进程 fan-out，该模式经官方验证

**降级路径**：保留一条走 RPC 协议的实现（vendor 内已含 `RpcClient`），用于快速验证与故障兜底。两条路径共用同一 `RunnerAdapter` 接口。

### 1.2.1 vendor 带来的架构简化

vendor 后可直接改内核，因此下列原本为绕开内核限制而设计的复杂度**变为可选**。但**在 M0 spike 验证前不要动手改** —— 先确认问题确实绕不过去，避免过早改动加重升级负担（候选改动点已登记在 [vendor/pi/PATCHES.md](../vendor/pi/PATCHES.md)）。

| 原设计（为绕开内核） | vendor 后的可选简化 | 判定时机 |
|---|---|---|
| `inMemory()` 注水 + 事件镜像实现持久化 | **已无必要** —— 存储层本就是接口（`Storage`），生产代码零 node builtin 依赖，实现自己的后端即可，无需改内核 | M0 Spike 2 ✅ |
| 外层分布式租约保证单写者 | 待定：需验证 JSONL 后端的并发写行为 | M0 Spike 2 |

> ⚠️ 原「给 bash 设默认超时」一项已随[安全策略决策 4](./security-policy.md) 失效 —— `bash` 工具默认不激活，改为结构化工具，故无需改动 `bash.ts`。若二期开放 bash，该项重新生效。

**改动纪律**（决定升级痛苦程度的不是 vendor 本身，而是改了多少、改在哪里）：

1. 优先顺序：**扩展钩子 > 包装层 > 改源码**
2. 必须改时统一标记 `// [TAO-PATCH] <原因>`，可 grep 一次列全
3. 每处改动登记到 `PATCHES.md`，不登记即技术债
4. 保留 vendor 自带测试 —— 改内核后靠它验证没改坏
5. `ai/` 下不做任何改动

### 1.2.2 与自有代码的边界

**业务代码不直接 import vendor，一律经由 `RunnerAdapter` 适配层。**

这样上游变更只影响适配层实现，不波及业务逻辑；将来若要更换内核或转为自研，改适配层即可。

> 这是「自主可控」的完整含义 —— 不只是"代码在我仓库里"，而是**"我随时能换掉它而不动业务代码"**。

### 1.3 Runner 生命周期

```
任务提交 → 编排器申请 Runner
   ├─ 温池命中（按 租户+镜像 键）→ 复用
   └─ 未命中 → 冷启动（拉起沙箱 + Agent Host）
          ↓
   注入：租户上下文 / 权限策略 / 技能清单 / 知识检索凭据 / 模型路由配置
          ↓
   执行（事件流实时上报网关与计量）
          ↓
   终态：完成 / 失败 / 超限 / 被取消
          ↓
   回收：镜像会话增量到数据库 → 销毁进程 → 清理临时卷
```

**关键参数**（一期默认值，可按租户覆盖）：

| 参数 | 默认 | 依据 |
|---|---|---|
| 单任务墙钟上限 | 30 分钟 | Pi 的 bash 无默认超时（审计 §6），必须外部兜底 |
| 单次 bash 超时 | 120 秒 | 同上 |
| Runner 内存上限 | 2 GB | 按 4 核 24 GB 环境，预留并发余量 |
| 单会话最大工具调用步数 | 200 步 | 防失控循环 |
| 温池空闲存活 | 10 分钟 | 平衡冷启动开销与资源占用 |
| 单租户并发 Runner | 按档位（免费 2 / 基础 5 / 专业 20） | 对齐 Spec 3.3 并发限制 |

## 2. 核心机制设计

### 2.1 异步任务与「执行中可继续对话」

这是 Spec 里用户最在意的能力。接口审计澄清了一个**必须修正的产品预期**：

> Pi 的 steering **不是工具执行中的打断**。消息落在当前 assistant turn 及其全部工具调用完成之后、下一次模型请求之前。**它永不取消执行中的工具，只有 `abort()` 能。**（审计 §5，对照 `agent-loop.ts:174-300` 验证）

因此产品的正确表达是「**已插入，将在当前步骤完成后送达**」，而非「立即打断」。原型与前端文案都按此口径。

**任务状态机**

```
     ┌──────────┐
     │ QUEUED   │ 排队中（等 Runner 或并发位）
     └────┬─────┘
          ↓
     ┌──────────┐   steer/followUp 入队 ┌─────────────┐
     │ RUNNING  │ ←────────────────────→│ 用户消息队列 │
     └────┬─────┘                       └─────────────┘
          ├──────────────→ ┌──────────────┐
          │                │ AWAIT_CONFIRM│ 等待确认（高危动作/信息缺口）
          │                └──────┬───────┘
          │                       ↓ 确认/拒绝
          ├───────────────────────┘
          ↓
   ┌──────┴───────┬────────────┬───────────┐
   ↓              ↓            ↓           ↓
SUCCEEDED     FAILED      CANCELLED    EXCEEDED
（可重试）    （保留中间物）            （超限，可续）
```

**事件桥接**：Pi 的事件（审计 §1 列出 11 个基础 + 14 个 session 事件）由计量扩展与宿主统一转成平台事件，经网关 SSE 推给前端。

> ⚠️ **两条不能搞错的语义**（审计 §1）：
> - `agent_end` **不等于**结束——重试、压缩、steering 都会越过它继续。**只有 `agent_settled` 表示 Pi 不会再自动继续**，任务终态判定必须用它。
> - `message_end.message` 是权威值，不要用 delta 自行拼接的结果落库。

**检查点与续跑**

Pi 自身不提供任务级检查点（它只有 session 树）。设计如下：

- 检查点单元 = **耐久 `OperationState` 的离散叶子**（13 个 family-neutral 状态），执行进度与消息历史在**同一次提交**里原子落盘
- Runner 异常退出后，编排器重新打开会话：`AgentHarness.create()` 内部调 `restoreSession()` 自动重建，并返回 `open: OpenOperation[]`（上次未跑完的操作清单）；对其调 `lane.resume()` 接力
- **不重复消耗的机制**（Spike 2 实读落盘文件确认）：任务完成时 `delete` 掉 `pi.op.meta` 与 `pi.op.state`，恢复时得到 `operation: null`，`resume()` 返回 `NothingToResume`，零模型调用。若崩溃在等模型响应时（`assistant.effect_pending`），恢复走 `recoverAssistantGeneration` —— 用已落盘的 `pi.pending.assistant_frame` 流式增量帧重建部分响应，**同样不重新调模型**
- 由此满足验收项「执行节点强制重启后从检查点续跑，已完成步骤不重复消耗模型调用」 —— [Spike 2](../spikes/02-checkpoint-resume/) 已用真实 JSONL 文件后端验证（5/5）

> ⚠️ 注水路径的 `persist = false`，不回写文件。故权威副本在数据库，Pi 的 JSONL 仅作运行时工作副本——这与约束 C 的结论一致。

### 2.2 子 Agent 并行

Pi 刻意不内置（审计 §3）。官方示例的真实做法是 spawn 子 `pi` 进程跑 `--mode json -p`，解析其 JSONL 并累加用量。

**采纳该模式，但收归平台管控**：

- 子任务不由扩展自行 spawn，而是**回调平台编排器申请子 Runner**——否则子进程绕过配额、审计与沙箱策略
- 主 Agent 通过自定义工具 `dispatch_subtask(goal, inputs, agent_profile)` 发起；工具实现向编排器下单，拿到子任务 id 后轮询/订阅结果
- 子 Runner 与主 Runner **同租户、同沙箱策略、独立会话上下文**，符合 Spec「子 Agent 间上下文隔离」
- 并发扇出度受租户档位与全局资源双重限制
- 失败回退：子任务失败时主 Agent 收到结构化错误，由其决定重试、降级或放弃

**代价与缓解**：每个子 Agent 一次完整进程启动。缓解手段为温池 + 只对「可并行且收益明确」的场景启用（多表核对、多份材料批量生成），不做无差别扇出。

### 2.3 权限门与沙箱

**权限门**（进程内，Pi 扩展实现）

用 `tool_call` 钩子做默认拒绝 + 白名单（审计 §6）。两条 fail-safe 特性对我们有利：
- `tool_call` handler **抛异常即阻断工具**
- 官方 `permission-gate.ts` 示例在 `!ctx.hasUI` 时默认阻断——正是无头 SaaS 的正确行为

策略来源：按 租户 × 场景 × 角色 下发的工具白名单。高危动作（对外发送、批量修改、删除）返回「需确认」，任务转 `AWAIT_CONFIRM`，前端弹确认卡片。

> ⚠️ `event.input` 原地修改后 **Pi 不再重新校验**（审计 §3）。因此改写参数的逻辑自身必须做完整校验，不能依赖 Pi 兜底。

**沙箱**（进程外，双形态必须分叉）

| 形态 | 实现 | 理由 |
|---|---|---|
| SaaS | microVM 级隔离 | 多租户高密度下威胁模型正确 |
| 私有化 | 容器 + seccomp 白名单 | **客户常拿不到 `/dev/kvm`**（客户自己跑在虚机里、嵌套虚拟化未开），microVM 方案直接装不上 |

两形态共用同一 `SandboxProvider` 抽象：`create / exec / pause / resume / kill` + 网络策略 + 资源上限。

**网络铁律（两形态一致）**：默认全断网，仅放通显式域名白名单，出网流量强制经审计代理。最常见的生产事故是隔离完美的沙箱配了无限制出网。

**工具级重定向接缝**：Pi 的每个内置工具都接受可插拔的 `*Operations`（`BashOperations`、`ReadOperations` 等），官方文档明确说是为了委派到远程系统。**这是把执行路由进按租户沙箱的干净接缝，无需 fork Pi。**

### 2.4 会话与状态持久化

**权威副本在 PostgreSQL，Pi 的 JSONL 是运行时工作副本。**

理由见约束 C。具体做法：

- 每个 Runner 用独立的 `sessionsRoot`（租户隔离 + 避免文件争用）
- **持久化直接用 `Storage` 接口自建后端**，不做「JSONL 落盘 + 事件镜像到数据库」的双写。`SessionRepo` / `Storage` 都是接口，生产代码零 node builtin 依赖，上游还导出 conformance 套件（`createStorageConformance`）供第三方后端自检合规 —— 实现自己的后端即可，不改内核（Spike 2 判定，详见 [PATCHES.md 候选 2](../vendor/pi/PATCHES.md)）
- 会话列表、搜索、分页全部走数据库索引 —— 一期若暂用 JSONL 后端，`JsonlSessionRepo.list()` 只读每个文件首行 header，可接受；但产品级列表仍走自建索引
- 恢复走 `AgentHarness.create()` → `restoreSession()`，返回的 `open` 数组即待续跑操作
- **分布式租约**：每个 session 同时只允许一个可写 Runner，用 Redis 租约 + 心跳实现。JSONL 后端零加锁（坏尾能自愈但并发写不保证），宿主必须自己保证独占；换数据库后端后该约束由数据库事务承担

**明确不做**（一期）：不 fork `session-manager.ts`（约 2000 行），不押注实验性的格式 4 `Storage`/`SessionRepo`（其文档自称 shapes 可能无迁移地原地变更）。

### 2.5 知识资产与记忆回写（核心差异化）

三类资产对应三种注入方式：

| 资产 | 注入机制 | Pi 钩子 |
|---|---|---|
| **文档知识库** | 自定义检索工具，按需召回；结果带来源标识 | `pi.registerTool` |
| **模板与字段口径** | 任务启动时作为约束注入系统提示 | `before_agent_start` 改 `systemPromptOptions` |
| **修改意见** | 同类任务启动时作为「上次的反馈」前置注入 | `before_agent_start` 或 `pi.sendMessage(deliverAs:"nextTurn")` |

**修改意见回写链路**（这是护城河的具体实现）：

```
用户在产物上提修改意见
   ↓
意见 + 产物 diff + 任务场景 → 结构化抽取（分类：格式/口径/措辞/事实/结构）
   ↓
落库为约束条目（scope: 平台/租户/工作区/个人，含来源任务 id 与置信度）
   ↓
下次同场景任务启动时按 scope 优先级合并 → 注入系统提示
   ↓
验收方式：对比两次同类任务产出，确认上次被改的地方这次不再犯
```

**检索隔离**：向量检索必须强制携带租户过滤，物理隔离租户（namespace 或强制 payload 过滤，取决于选型），并为每个过滤字段建索引。分页后置鉴权，**绝不用大集合的 ListObjects 做预过滤**。

**权限读写分离**：知识库授权必须区分「可查看」与「可编辑/删除」——这是企业客户第一天就会提的需求（Dify 的已知缺陷正是授权即全权限）。

### 2.6 技能体系

Pi 的 skill 机制可直接复用，但有一个关键约束（审计 §7）：

> **没有专门的 skill 加载工具——触发方式就是对系统提示中所告知的绝对路径发起一次普通 `read` 调用。**

两个后果必须在设计中体现：
1. **不能禁用 `read`/`bash`**，否则模型自主调用 skill 失效
2. **skill 路径必须对工具所在沙箱可读** —— 沙箱挂载必须包含技能目录

**三级命名空间**（对齐 Spec 3.6）：平台共享 / 租户私有 / 会话临时，按优先级合并。

**动态注册**：用 `resources_discover` 钩子或 `skillsOverride` 在内存中构造 skill 对象。但**正文仍须落在某个路径上**，故实现为：数据库/对象存储是真源 → Runner 启动时按租户绑定关系物化到沙箱内临时目录 → 通过钩子声明发现。会话临时技能设生存期自动回收。

### 2.7 模型路由与成本

Pi 的 `pi-ai` 已提供多提供方统一接入与会话中途换模型（审计 §1），直接满足 Spec「模型可热替换」的硬要求。

**分层路由**：
- 默认轻量档执行
- 旗舰档仅用于任务规划与结果裁决节点（用 `scopedModels` 或运行时 `set_model`）
- 必须开启上下文缓存 —— 这是最大单点成本杠杆

**路由变更门禁**：覆盖两个行业核心场景的回归用例集，上线前必过。**静默质量退化不报错、不上仪表盘，两三天后以客服工单形式出现** —— 这条必须做成 CI 门禁而非人工约定。

**成本护栏**：
- 单用户级熔断（1% 的重度用户足以击穿席位制毛利）
- 计量埋点两形态完全一致；**结算层分叉**：SaaS 扣额度并熔断，私有化只上报不扣费、配额转为并发与速率硬限
- 额度向用户呈现的单位是**产物与任务**，不是会话次数（一个多步任务可能几十次工具调用但只交付一个 docx）

### 2.8 Office 产物与格式保真

直接对手的公开短板正是「导出到 WPS/Office 后格式跑偏」，这是可攻击的正面战场。

- 走**原生文件生成**路线（非 HTML 转换），产物真可编辑、可盖章流转
- 基于机构模板套版，保留公式与数据格式
- **生成后必须打开校验**：校验版式与可打开性，失败则自动重试或降级并告知用户
- 产物与源数据、任务、被引用知识片段保留关联，支持逐项追溯

## 3. 数据模型要点

**铁律：所有业务表无条件携带 `tenant_id`，并施加行级安全。私有化部署时租户数为 1，但模型不简化。**

这是双形态共用一套代码的前提，也是租户可在两形态间迁移的前提。**明确排除 schema-per-tenant**（云厂商官方定性为运维复杂且不更安全的双输区间）。

核心实体（字段略）：

| 域 | 实体 |
|---|---|
| 组织 | `tenants` / `workspaces` / `users` / `memberships`（角色） |
| 会话与任务 | `sessions` / `session_entries`（镜像 Pi 树，保留 id/parentId）/ `tasks` / `task_checkpoints` / `task_events` |
| 知识资产 | `knowledge_bases` / `documents` / `chunks` / `templates` / `field_definitions`（口径）/ `feedback_constraints`（意见回写）|
| 技能与场景 | `skills` / `tenant_skills` / `scenario_cards` / `scenario_versions` |
| 产物 | `artifacts` / `artifact_lineage`（溯源） |
| 计量 | `usage_events`（统一事件流）/ `quotas` / `billing_records` |
| 审计 | `audit_logs`（工具调用、权限拦截、资产变更、技能启停） |

**索引与隔离要求**：
- 所有查询路径的复合索引首列为 `tenant_id`
- 向量检索强制租户过滤 + 过滤字段建索引
- 会话列表走独立索引表，不做全量扫描

## 4. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| Agent Host | **TypeScript / Node ≥ 22.19** | vendor 的 Pi 内核是 TS，扩展由 jiti 转译无需构建；Node 版本是 Pi 的硬要求 |
| 平台服务 | TypeScript（NestJS 或 Fastify） | 与 Host 同语言，类型可共享，团队单一技术栈 |
| 前端 | React + TypeScript + Vite | 生态成熟；Pi 另提供 Lit 版 Web 组件库可作聊天区参考 |
| 数据库 | PostgreSQL（行级安全） | RLS 原生支持租户隔离；单库支撑双形态 |
| 缓存与队列 | Redis（缓存 + 租约 + 轻量队列） | 私有化单机部署可用，不引重组件 |
| 对象存储 | S3 兼容（私有化可用 MinIO） | 产物与技能包存储，双形态一致接口 |
| 向量检索 | 一期用 PostgreSQL 向量扩展 | **私有化优先**：少一个组件就少一份客户运维负担；规模上来再抽到独立服务 |
| 沙箱 | SaaS microVM / 私有化 容器+seccomp | 约束 B，物理限制导致必须分叉 |
| 部署 | 单机 Compose（私有化默认） | 客户不具备编排运维能力 |

**选型原则**：私有化形态的组件数量是交付成本的主要来源。**每多一个有状态组件，就多一份客户运维负担与故障面。** 因此一期刻意把向量检索放在 PostgreSQL 内，不引独立向量库。

### 5.3 M0 的三个 spike（写代码前必须做）

接口审计列出的关键未知，必须用实验而非推理来消解。代码在 [spikes/](../spikes/)，`npm run spike` 可复跑。

约定：**每个 spike 必须含反向验证用例** —— 断言若在任何情况下都通过，它就只是装饰。这条规则在 Spike 1b 上立刻见效，反向用例失败暴露了 `findEntries` 的用法错误，否则三个「不含对方内容」的断言会因读到空数据而假通过。

**Spike 1 · 并发隔离验证 —— ✅ 已完成，10/10 通过**

目标：证伪或确认「进程内多 session 不可行」。

**实测结论与审计阶段的推测相反：隔离是成立的。** 审计当时预判「有 4 个全局单例，预期失败」，实际全量扫描 `src/` 后确认——消息历史 100% 挂在实例上，进程级可变状态只有一处（`stream-fn.ts:3` 的 `defaultStreamFn`，仅一个函数引用，不持有会话状态）。底层 `Agent` 与 `Harness + Session` 两层各自并发执行，消息历史、模型侧 transcript、事件流三者均不串台；6 个会话并发同样隔离。

验证手段上做了两件关键设计：让 A 慢 B 快产生**真实时间交错**（共享状态最容易在交错时暴露）；检查**模型侧收到的 transcript** 而非仅本地历史——上下文若混入对方内容，说明泄漏已发生在出网请求里。

由此确立两条 M1 硬约束：

1. **多用户必须一人一 Session。** 同一 Session 下的多个 lane 在 Session 的 mutation line 上**串行**执行，「一租户一 Session、每用户一 lane」会让用户互相排队。
2. **`RunnerAdapter` 必须显式传 `streamFn`。** 省略即落到那处进程级全局，多会话共用同一模型入口。它在**构造期**解析，缺省时启动即崩（而非运行中崩），这一点反而有利于尽早发现配置错误。

> 架构决策不变：**仍走一会话一进程**。隔离虽成立，但沙箱隔离需求独立存在（安全策略要求执行环境相互不可见），且进程级隔离额外提供故障域隔离。本 spike 的价值在于：确认了「单进程内多会话」在开发调试与轻量私有化部署下是安全可用的后备形态。

**Spike 2 · 检查点续跑 —— ✅ 已完成，5/5 通过**

目标：验证持久化路径能否支撑续跑，且已完成步骤不重复消耗模型调用。

**两处对最初假设的修正**（都来自实读源码）：

1. **审计描述的 `SessionManager` 属于另一套实现，我们用的不是它。** 上游存在**两套并行的会话实现**：

   | 实现 | 位置 | 特征 | 我们的取舍 |
   |---|---|---|---|
   | `SessionManager` | `coding-agent/src/core/session-manager.ts`（2010 行） | 私有构造、硬依赖 `node:fs`、零加锁、`list()` 为 O(所有字节) —— 审计描述的问题**均真实存在** | **未 vendor，不使用** |
   | `SessionRepo` + `Storage` | `agent/src/harness/session/` | 两层接口、生产代码**零 node builtin 依赖**（文件系统是注入的 `FileSystem` 能力）、上游导出 conformance 套件供第三方后端自检 | **产品采用** |

   因此「换数据库后端需 fork 2000 行文件」对我们不成立 —— 实现自己的 `Storage` 即可，**不改内核**。原设计里「`inMemory()` 注水 + 事件镜像」的绕行复杂度可直接删除。
2. **「不重复消耗」只在 harness 层成立，底层 agent-loop 不成立。** `runAgentLoop` 被调一次就必然发起至少一次模型请求；`Agent.continue()` 在历史尾部是 assistant 时**抛错**而非幂等跳过。产品必须走 harness 层。

**幂等性的根源**（实读落盘 JSONL 确认）：任务完成时 `delete` 掉 `pi.op.meta` 与 `pi.op.state`，恢复时 `restoreLaneState` 得到 `operation: null`，`resume()` 返回 `NothingToResume`。另有 `pi.pending.assistant_frame` 机制 —— 崩溃在等模型响应时，靠已落盘的流式增量帧重建部分响应，不重新调模型。

> 本 spike 用**真实 JSONL 文件后端**验证，因为上游 harness 层的 resume 测试全部跑在 `MemoryStorage` 上 —— 「真进程重启」这条端到端路径是上游测试的空白，而它恰是我们的验收标准。

**Spike 3 · 权限门与工具注册 —— ✅ 已完成，7/7 通过**

目标：验证默认拒绝 + 白名单能否真正拦住执行，以及能否用结构化工具替代自由 shell。

钩子机制位于 agent 包内（`src/harness/hooks.ts`，11 个钩子），权限门用 `before_tool` 返回 `{ block: { reason } }`。四条经验证的关键性质：

| 性质 | 对安全模型的意义 |
|---|---|
| 被拒调用的 `execute` **零次**被调用 | 不是「返回错误」，是真的没执行 |
| handler 抛异常 → **fail-closed** | 权限逻辑有 bug 时行为是拒绝而非放行 |
| 被拒调用**不写执行意图** | 崩溃恢复不会重放曾被拒绝的高危调用 |
| 内置工具是工厂函数，**源码无任何自动注册** | 不调 `createBashTool()` 就没有 bash —— [安全策略决策 4](./security-policy.md) 的前提成立 |

**生产形态**：`activeToolNames`（模型侧不可见）+ `before_tool`（执行侧兜底，防历史 transcript 里的旧工具名被重放）两层叠加，并订阅 `handler_error` 监控权限代码自身异常。

> 注意 `before_tool` 返回 `{ args }` 会**重新做 schema 校验**（legacy `beforeToolCall` 不校验）。若在钩子里注入默认值，注入后须仍满足 schema。
