# M5 · 账号、持久化与 Web 前端

M4 交付了私有化交付包与可真实启动的服务，但服务形态仍是「单租户、内存态、只有 API」。
M5 把它推进到 requirements 第 3、4 章定义的**一期 SaaS 形态**：真实账号与租户隔离、
重启不丢的任务与审计、桌面与移动 Web 前端，以及拦得住纯文本生成的 provider 层熔断。

> 延续 M4 的判断顺序：**先落盘，再谈账号与界面**。数据不可信时，账号体系下钻、
> 任务中心、前端展示都建立在会被一次重启清空的状态上，没有意义。

## 起点与约束

| 已具备（M4 末） | 仍缺 |
|---|---|
| 计量 JSONL 落盘、按月分片、逐行容错（[Spike 8](../spikes/08-append-durability/) 验证） | 任务状态、事件历史、审计日志都在内存，重启即丢 |
| 任意非空 token → 单一默认租户；`admin:` 前缀判管理员 | 真实账号 / 租户 / 用户三层、角色落数据 |
| 用量按工作区下钻（记录里无 userId） | userId 进用量记录、按人下钻 |
| 熔断挂在 `before_tool`，拦不住「只生成长文本」 | provider 层在模型调用前熔断；强弱模型分层路由 |
| HTTP API + SSE 完整 | 无任何 Web 界面 |

**硬约束（沿用前四个里程碑）**：

- 私有化默认单机 Compose、2 小时装成 —— **不引入需要原生编译的依赖**，
  不引数据库（Spike 8 已证 JSONL 足够），不引重型前端构建链。
- 前端与原型（`prototype/`）是两个产物：原型用于需求评审与交接，
  M5 的前端是**接真实后端**的可用界面，但视觉与交互直接复用原型已验证的设计，不另起炉灶。
- 业务包与 vendor 内核保持边界（`npm run check:boundaries`）。

## M5-1 · 持久化

### 三类数据、三种写模式

不把所有东西塞进一个文件——它们的写模式不同：

| 数据 | 写模式 | 形态 |
|---|---|---|
| 审计日志 | 只追加、按时间查 | JSONL 追加（同计量），按天分片 |
| 事件历史 | 只追加、按 taskId + seq 查 | 每任务一个 JSONL（事件随执行顺序追加，seq 单调） |
| 任务记录 | 状态机多次改写（queued→running→…） | 状态变更追加到任务变更日志，**当前态为变更流折叠结果**；启动时回放得到 |

任务记录不用「每次状态迁移整份覆写快照」作为唯一来源——覆写在 kill -9 时可能留下
半文件。改为**追加状态变更 + 启动回放**，当前态是变更流的折叠结果（事件溯源的最小形态）。
这天然免费得到审计所需的「任务何时被谁改成什么」轨迹。

### 进行中任务的恢复语义（必须诚实，不能假装能续跑）

进程重启时处于 running 的任务，其**会话上下文仍在内存里丢失了**（M5-1 不解决会话续跑，
那需要把 Pi SessionRepo 接到落盘 FileSystem，单独一项）。诚实的恢复语义：

- running 任务重启后标记为 **`INTERRUPTED`**（新状态），不是假装还在跑，也不是判失败；
- 用户可对它发起「从最后成功检查点重试」——这条链路 M3 的检查点机制已具备数据基础；
- waiting（待确认）任务恢复为 waiting，确认后继续；queued 任务恢复排队，等名额启动。

不允许出现「列表显示 running 但没有任何执行器」的僵尸态（原型评审中已多次踩这个坑，
后端不能重蹈）。

### 接线边界

- 在 knowledge 包新增文件型任务存储与审计存储（与 `file-metering-store` 同风格）；
- orchestrator 的 `TaskOrchestrator` 依赖注入存储接口，默认仍可内存实现，main.ts 装配文件版；
- 事件统一重编号（M4 评审修复已立 `ingest`）落盘时复用同一写入口，不新增序号空间。

### 本项产出

| 模块 | 职责 |
|---|---|
| [task-store.ts](../packages/core/src/task-store.ts) | 持久化契约：TaskStore / AuditStore、StoredTask、TaskChange；`listAll` 仅限启动恢复 |
| [file-task-store.ts](../packages/knowledge/src/file-task-store.ts) | JSONL 文件实现：tasks/ 变更流、events/ 事件流、audit/ 按天分片；taskId 白名单防路径穿越 |
| [memory-task-store.ts](../packages/knowledge/src/memory-task-store.ts) | 内存实现（测试与开发态），与文件版共用折叠函数 `foldChange` |
| [task-orchestrator.ts](../packages/orchestrator/src/task-orchestrator.ts) | 注入 TaskStore；变更/事件随 ingest 落盘；新增 `recover()` |

### 真实验证（kill -9）

起服 → 提交任务 → 任务进入 RUNNING（用挂起的假模型端点让它一直执行）→ `kill -9` 服务
→ 同一工作区目录重启：

- 启动日志打印 `[恢复] 1 个任务在服务重启时处于执行中，已标记为中断：<taskId>`；
- 该任务状态为 **INTERRUPTED**、带可读原因，**不是**无执行器的僵尸 RUNNING；
- 事件流文件含完整 QUEUED→RUNNING 序列，可断线重连；
- 第三次再启动：0 条恢复记录、状态保持 INTERRUPTED —— 恢复结果已落盘，不重复判定。

终态任务（成功/失败/取消）与 QUEUED 任务重启后原样恢复，由单测覆盖。

### 能力边界（诚实）

- **会话上下文不续跑。** 重启只恢复可读的任务列表、事件与审计，不重建 Runner；
  INTERRUPTED 任务需用户从检查点手动重试。让会话本身可续跑要把 Pi 的 SessionRepo
  接到落盘 FileSystem，是 M5 之后单独一项，不在 M5-1 内。
- **恢复是单进程假设。** 同一时刻只允许一个服务实例使用同一工作区目录
  （单机 Compose 形态本来如此）；多实例共享目录的租约仲裁属 SaaS 形态。

## M5-3 / M5-4 · Web 前端（已完成）

前端是独立产物 `web/`（与评审用 `prototype/` 分开），纯静态、零依赖、零构建，
由 server 同源托管（`static.ts`，鉴权前提供，含路径穿越防护），镜像通过
Dockerfile 拷入 `/app/web`。复用原型的设计变量与组件样式，数据全部走真实 API。

- 页面：根 `login.html`；桌面 `workbench / session / tasks / knowledge / admin`；
  移动 `tasks / session`。
- 为前端补齐的后端接口：`GET /api/me`、`GET /api/scenarios`、
  `POST /api/files`（multipart 上传，零依赖解析，含中文名 RFC 5987 兼容）、
  `GET /api/files` / `GET /api/files/:name`（资料库列举/下载）、
  `GET /api/tasks/:id/events`、产物下载 `GET /api/tasks/:id/artifacts/:name`、
  动作 `confirm / reject`。
- 产物事件接线：办公工具成功结果里的 `details.outputPath` 由适配层转为
  `artifact` 事件，编排器累积进任务产物并随变更流持久化，前端据此给下载入口。
- 鉴权：普通接口走 `Authorization: Bearer`；EventSource 不能自定义头，SSE 与
  文件下载这两类浏览器无法带头的 GET 允许一次性 `?access_token=`（预签名式），
  其余接口一律不认 query token。
- SSE 复用 M4 的 `flushHeaders` + 心跳 + Last-Event-ID，前端订阅后按 seq 去重、
  叠加 5–8 秒轮询兜底。

**能力边界（诚实记录）**

- 知识页当前是**工作区文件级资料库**（上传/列举/下载，文件可被办公工具直接读）。
  向量语义检索、模板/口径库、修改意见回写的内核能力已就绪，但其独立落盘库与
  Web 管理界面未在本期开放，页面已显式说明。
- 高危确认链路：状态机的 `confirm/reject` 与前端卡片已接通；当前预置工具均未标
  `requiresConfirm`，故默认场景不会进入 AWAIT_CONFIRM。gate「批准后重放被拦下的
  那一次工具调用」在内核层仍需补一条挂起/放行通道，作为后续项；不影响现有场景。

## M5-5 · provider 熔断与模型路由（已完成）

- **出网前配额闸**：落在 `InProcessRunner.prompt()` 第一次模型调用之前
  （`HostRuntime.preflightModel`，拿得到租户与档位）。超限时直接抛错、不触碰
  `lane.prompt`，因此零字节出网、零模型消耗，编排器把任务转 FAILED 并给可读理由。
  它与 `before_tool` 闸共用同一份 meteringStore / quota / 单价表（看板与闸门一本账）。
  未配配额（私有化默认）返回 undefined，不拦截。
  - 最初尝试在 provider API 外包一层装饰流，但内核只以类型导出
    `AssistantMessageEventStream`，宿主无法自行构造终止流，故改为在 runner 接缝拦截。
- **双档模型**：`MODEL_*` 为旗舰、`MODEL_LITE_*` 为可选轻量；三项要么全配要么全空
  （半配拒绝启动）。两档不同 baseUrl/key 时各注册一个独立 provider。
  `RunnerSpec.tier`（词汇留在 @tao/core）在创建 Runner 时选模型，整次 run 用同一档，
  **计量落账的模型名取实际档位 id**，避免轻量 token 按旗舰价错算。价格表两档各一行，
  轻量缺价会进 unpricedModels；启用金额配额时强制要求两档单价齐备。
- **能力边界**：内核 harness 路径在一次 run 内不按「规划轮/执行轮」动态换模型
  （只能整 lane 切档），故分层粒度是「每次 Runner 运行一个档位」。当前提交链路
  默认走旗舰；子 Agent（fanOut）可在创建子 Runner 时指定 lite，场景卡级别的
  分档策略作为后续接线项。

## 验收门禁

- 全链路持久化：起服→多任务（含排队、待确认、成功、失败各态）→ kill 进程→重启，
  任务、事件、审计、用量全部可恢复，无僵尸 running。
- 真实隔离：两个账号互不可见对方任务与用量；普通成员访问管理接口 403。
- 前端全链路：浏览器（桌面 + 375px 移动模拟）走完核心用户旅程。
- provider 熔断：超配额账号提交纯文本任务，第一次模型调用前被拒，零模型消耗。
- 既有 895 项测试与边界检查持续通过。

## M5-2 · 账号与租户（已完成）

### 形态取舍

私有化单机、账号少且不常变 → 账号存工作区根下一份静态 `accounts.json`，
运维直接编辑、随部署分发，不做账号增删 API、不引数据库。SaaS 形态把
`authenticateToken` 换成真实身份服务即可，调用契约不变。

- **token 精确查表**得到租户/工作区/用户/角色，废除 M4 的「任意非空 token 进默认租户」
  与「`admin:` 前缀判管理员」；查不到即匿名 401。
- 首启落默认种子（管理员 + 成员两个占位账号），文件权限 0600，启动时对 `change-me-`
  占位 token 打醒目安全警告；账号文件坏/校验不过直接拒绝启动。
- **userId 进用量记录**：`UsageRecord` 增加 userId，落账在 agent-host 适配层从
  `TenantContext` 取；看板新增真正的**按用户**下钻，保留**按工作区**维度。
  M4 旧分片无 userId，读取时归入「未知用户」，不报错也不散成多组。

### 真实验证（鉴权矩阵）

| 请求 | 结果 |
|---|---|
| 成员 token → /api/admin/usage | 403 |
| 管理员 token → /api/admin/usage | 200 |
| `admin:<任意>` 前缀 | 401（旧规则已废除） |
| 任意不认识的 token / 无 token | 401 |
| 成员 token → /api/tasks | 200 |

### 能力边界

- 账号仍是**静态文件**，没有注册/改密/会话过期/SSO；SaaS 形态接统一身份认证
  （需求 3.8）是后续工作。
- 私有化固定单租户；多租户隔离的行级过滤已就位（账号可属于不同 tenantId），
  但没有租户管理界面。
